## Decisions made (and why)
- **The meter's filter class is pyloudnorm's `"DeMan"`**, not its default `"K-weighting"`.
  - KNOW (probe): DeMan's coefficients at 48 kHz match BS.1770-4's table to 1e-8, and a −20 dBFS
    997 Hz sine reads −23.010 LUFS.
  - The default class (RBJ cookbook filters) reads −23.052 LUFS.
- **pyloudnorm counts a final partial block** because it rounds the block count, so it reads up to
  0.059 LU lower than whole-block gating on the real paragraphs. With pyloudnorm's own block count
  reproduced, the difference is exactly 0. This is within EBU Tech 3341's ±0.1 LU, is documented in
  `loudness.py`, and the evidence test uses that tolerance.
- **The resampler filter** replaces scipy's default (Kaiser β 5, 10 zero crossings).
  - The default is −1.1 dB at 11 kHz and only −18.5 dB at 13 kHz for 24 → 48 kHz.
  - The pinned design is flat to 11 kHz and ≤ −75 dB from 13 kHz (KNOW: `freqz`), and costs 36 ms per
    40 s.
- **True peak** uses BS.1770-4 Annex 2's method (4× oversampling, the maximum absolute value), with the
  pinned interpolation filter in place of the Annex's 48-tap example.
  - The original samples are included, so the true peak is never below the sample peak.
  - The ceiling is checked on the final quantised file. When it is exceeded, the gain drops at once to
    what the ceiling allows (the true peak is linear in the gain), then in 0.0001 dB steps while
    quantisation keeps it above.
- **The gain is rounded to 0.0001 dB before it is applied.** The record's `gain_db` is then exactly the
  gain used, and float noise in the measurement (for example, SIMD differences between CPUs) cannot move
  a sample. `measured_lufs` and `true_peak_dbtp` are measured on the final file and rounded to 0.0001.
- **Quantisation is ours:** `rint`, half to even, then clipping. libsndfile only packs left-aligned
  int32. KNOW: every 24-bit extreme survives the round trip exactly, and the header is a canonical
  44 bytes, identical on every write.
- **Fades are raised cosine**, 480 samples at 48 kHz, and the first and last samples are exactly 0. The
  design gives no fade shape.
- **Less silence than `pad_s` at an end** (common: 5 of 48 real heads and 23 of 48 real tails, 1 with no
  tail at all): all of it is kept and nothing is added. The length is therefore
  raw − max(head − pad, 0) − max(tail − pad, 0), and the record's `head_s`/`tail_s` state the silence
  found. See question 2.
- **`GAIN_HIGH` compares the gain applied** (the record's `gain_db`) with +12 dB, not the gain the target
  asked for, so the record and the flag never contradict each other.
- **Degenerate takes are delivered, not refused**, so that QA fails them and triggers a retake:
  - non-finite raw samples are treated as 0 (`SignalStats.raw_nonfinite` reports them);
  - digital silence is not trimmed and gets no gain;
  - an empty raw gives an empty file;
  - under 400 ms, the take is measured as one block with silence after it (BS.1770-4 defines nothing
    shorter). This asks for more gain than the take's own length would, and the ceiling may then win.
- **`SignalStats`**:
  - clipping counts raw samples with |x| ≥ 32767/32768, infinities included;
  - the DC offset is the raw mean, with non-finite samples as 0;
  - the voiced bounds and the longest internal silence use the trim's speech rule at −40 dB on the
    delivery, at 20 ms resolution.
- **CPU thread cap (§4.1):** the pipeline uses no BLAS and no threaded primitive. `resample_poly`,
  `lfilter` and numpy's element-wise operations run on one thread. KNOW: a subprocess test samples the
  process's native thread count during `deliver` and finds no new thread. There is therefore nothing to
  cap inside `narration.post`. The environment variables (`OMP_NUM_THREADS` etc.) are the daemon's to
  set at spawn, beside WP16's worker set-up.
- **Tool strings** (`delivery_tools()`) name each component, its installed version (importlib.metadata)
  and its pinned parameters, plus the scipy and numpy versions underneath. For example:
  `scipy.signal.resample_poly 1.18.1 (firwin kaiser beta=8.6, 32 zero crossings, padtype=constant;
  numpy 2.5.3)` and `pyloudnorm 0.2.0 (BS.1770-4, filter_class=DeMan, mono weight 1.0; true peak 4x
  oversampled with the pinned resampler; scipy 1.18.1, numpy 2.5.3)`.
- **Evidence tests never write bakeoff-derived audio:**
  - each paragraph is processed in memory;
  - the cross-process check prints a hash;
  - the one `process()`-by-path test deletes its output in `finally`.

## Contract change requests
1. **`narration.contracts.models.DeliveryTools`** (hence the delivery key): add a version of
   `narration.post`'s own rules, e.g. `post: str = "narration.post/1"`.
   - Why: §10.2's key names the "trim rule", but `DeliveryConfig` holds only the rule's parameters. A
     change to the frame layout, the percentile method, the fade shape, the quantiser, the gain rounding
     or the ceiling procedure would change the bytes while the delivery key stayed the same.
   - Until then: no workaround in code; any such change must come with this field.
2. **`models.Loudness.measured_lufs` and `true_peak_dbtp`**: make them nullable (`float | None`, always
   present) for a take with no defined loudness (every block under the −70 LUFS gate) or an all-zero file.
   - Why: JSON cannot carry −∞.
   - Local workaround (documented in `pipeline.py`): `measured_lufs = −70.0` ("at or below the absolute
     gate"), and `true_peak_dbtp` = one LSB (−138.47 dB for PCM_24).
   - Or the lead keeps these floors as the contract.

## Questions for the lead / owner
1. **The loudness target is not reachable on real output (KNOW, above).** With −1.0 dBTP, no limiter and
   Qwen's 15.7–20.3 dB peak-to-loudness ratio, every one of the 48 bakeoff paragraphs was held under
   −16 LUFS (by 0.7–5.3 dB, median 2.8 dB). Takes of one script therefore differ by up to 4.6 LU.
   - The design accepts this ("the ceiling wins"; callers level with the record), but it seems to
     assume the ceiling is the exception. Options, for the owner:
     - (a) keep the design;
     - (b) lower `target_lufs`: of these 48, a −18 target is reached by 11, −19 by 26, −20 by 40;
     - (c) add a true-peak limiter: a design change, since §13 says "no limiter".
   - A proposed DC, if wanted.
2. **Less silence than `pad_s`** at an end is common in real takes. Is keeping what exists (implemented)
   right, or should the delivery be padded with digital silence so that every take has exactly `pad_s`
   before its first and after its last speech frame? The latter makes §13's formula literal.
3. **plan.md §1.2 and WP13** name the takes `outputs/qwen3-tts-1.7b-clone-{d2,d4}-seed{1,2,3}`. The actual
   folders are `…-clone-d2-late-night_take1-seed1` and so on, and the files are PCM_16 at 24 kHz, not
   float32. The evidence test globs `qwen3-tts-1.7b-clone-*`. A plan wording fix only.
4. **Deduplication with WP16:** if WP16 defines the thread-cap environment for workers, the daemon's own
   start (WP30/WP31) should reuse it. `narration.post` needs none.
