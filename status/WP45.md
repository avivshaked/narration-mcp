## Done
- **`narration-admin voices allow <clip.wav> [--yes]`** (`src/narration/admin/voices.py`):
  1. The configuration is `find_config`'s, and it must load before it is changed. A file that does not load
     is refused with `load_config`'s message (exit 2), and nothing is asked.
  2. The clip's path is made absolute with `os.path.abspath`, after `~` is expanded, and then checked by the
     platform (`Platform.check_readable_path`, §17.3). So a relative path is taken from the operator's
     working folder. On Windows, this also normalises the path the Windows way before the check sees it:
     - `C:clip.wav` (drive-relative) and `\clip.wav` (rooted) become absolute;
     - a trailing dot or space on a name is dropped.

     Windows opens the same file either way, and the hash and the note name the file the check resolved.
     A refusal keeps the platform's hint (on an unsupported OS: Windows only).
  3. The file is read once, at most 20 MB (`MAX_CLIP_BYTES`). The bytes that are hashed are the bytes checked
     by `soundfile` to be a WAV (`WAV_FORMATS`) with audio in it. Refused (exit 1, nothing changed):
     - a path the check refuses;
     - an unreadable file, or one over 20 MB;
     - not audio, not a WAV (e.g. FLAC), or a WAV of 0 frames.
  4. It prints the clip's path, length (with the rate and channels), sha256 and the configuration file.
  5. It warns (stderr) when the clip is longer than `[limits] max_clip_seconds`: the service would refuse to
     clone it (`UNSUPPORTED_AUDIO`) as the limit stands.
  6. A hash already listed (compared without regard to case) changes nothing, asks nothing, and exits 0.
  7. A read-only configuration file is refused before the question, with what to add by hand.
  8. It asks: "Is this clip synthetic? Type yes to allow it:". **Only `yes`**, typed in full (any case,
     surrounding spaces ignored), goes on; `y` does not.
     - Any other answer changes nothing and exits 1. So does no answer at all: end of input, or a closed or
       missing stdin.
     - The no-answer message says a person must confirm (the operator, in a terminal, types yes), that an
       agent or MCP client must not allow a clip, and that `--yes` is only for the operator's own scripts.
       `--help` says the same of `--yes`. `--yes` skips the question.
  9. The hash is added in lower case with the comment `# <the clip's resolved path>`. Control characters are
     replaced, so a file name cannot end the comment and write TOML.
     - The edited file must load with `parse_config` and give the same value for every other setting. The
       values are compared by `repr`, so a NaN setting does not refuse.
     - It is written to `.narration.toml.<hex>.tmp` beside the file and fsynced, and gets the file's POSIX
       mode bits (`shutil.copymode`; on Windows only the read-only flag). Then it is renamed over the file
       with `os.replace`.
     - **Before every rename attempt the file is read again.** If it changed (or is gone), nothing is written:
       exit 1, "changed while this command ran … Run it again". A Windows sharing refusal of the rename or of
       the read is retried for about a second, and each retry reads the file first (review F1).
     - A short window remains between that read and the rename, because there is no lock between writers.
       Two `voices allow` runs at the same moment can lose one hash.
     - Not carried over: the file's owner and group, its ACL and other attributes. The renamed file is a new
       file, with those of a new file in the folder.
     - Any failure leaves the file as it was, removes the temporary file, and prints what to add by hand.
  10. **What to add by hand** fits how the file writes the list (`allowlist.hand_edit`):
      - a multi-line array: the line `"<sha>",  # <path>`;
      - a one-line array or an inline `voices = {...}` table: the bare value `"<sha>"`, with no comment,
        since a comment would swallow the rest of the line;
      - no `allow_sha256`: `allow_sha256 = ["<sha>"]` for `[voices]`.
  11. It ends by saying what to restart, the daemon first (next section).
- **`narration-admin voices list [--json]`**: each hash, with the comment on its line; an empty list says
  so and how to add a clip.
- **What reads `allow_sha256`, and when** (read in the code, and pinned by the acceptance test):
  - **The front-end** (`narration-mcp`, one per MCP client) loads the configuration once, at start
    (`narration.mcp.__main__.main` → `load_config(find_config(...))` → `serve`). `NarrationBackend` checks
    the list in `submit_job`, `measure_voice` and `audition_pronunciation` (`check_synthetic`).
  - **The daemon** loads it once, at start (`narration.daemon.__main__.main` → `load_config(args.config)`).
    It checks the list again when it opens a job: `generate` in `narration.jobs.engine`, `measure` in
    `narration.measure.handler` (both `require_synthetic`).
  - So **both must be restarted, the daemon first** (review gate F3). A front-end restarted while the old
    daemon runs would admit a job that the old daemon then fails. The command says, in order:
    1. `narration-admin daemon stop`. The next job starts the daemon again, or run `narration-admin daemon
       start` when `[daemon] autostart` is off. If no daemon runs, there is nothing to stop.
    2. Restart or reconnect `narration-mcp` in every client that runs it.

    It also says that a server or daemon started with another configuration file does not read this one.
    (`narration-admin render` builds its own front-end each run, so it reads the file each time, but its
    jobs run in the daemon.)
- **The TOML edit** (`src/narration/admin/allowlist.py`): a careful text edit, not tomlkit (see Decisions).
  - `_Scanner` walks the file as TOML does: headers, keys of every form, strings of all four kinds, arrays,
    inline tables, and the other scalars, with comments and newlines between them. So a `[voices]` inside
    a multi-line string is never taken for the header.
  - It appends the item on its own line, copying the indent of the other items, and adds a missing comma
    after the item before it. It opens a one-line or empty array onto lines.
  - A missing key goes into `[voices]` after the comment lines directly below the header. A missing table
    goes at the end of the file after a blank line.
  - **New lines end as the edit site does** (review TOML F3): the `]`'s line, the `[voices]` header's line,
    or the file's last line. So a file with mixed endings keeps each part's.
  - The edited text must parse (`tomllib`) to the original plus the one hash, or nothing is returned.
  - An inline `voices = {...}` table is refused, with the bare value to add by hand.
- **`Admin.ask`** (`cli.py`): prints a question and reads one line from `Admin.inp` (stdin by default). It
  returns None when stdin is closed, missing (`pythonw`) or at its end. `main()` takes `inp` for tests.
- `voices` added to `COMMAND_GROUPS` (after `render`).
- Docs: a CHANGELOG entry; one sentence in README.md ("Use it from Claude Code", step 3); two comment lines
  in `narration.example.toml`'s `[voices]`.

## Decisions made (and why)
- **A careful text edit, not tomlkit.** The lead approved tomlkit. I added `tomlkit==0.15.1` (MIT, the latest)
  and tried it on the cases above first.
  - Its `Array.add_line(value, comment=...)` put the closing `]` inside the new comment for a one-line array,
    an empty array, a dotted key and an inline table, which made the TOML invalid.
  - It put a missing key after the comments that belong to the next table.
  - It wrote LF lines into a CRLF file.

  Working around that needs its private API. The text edit gets all of these right. Every edit is verified
  by `tomllib` and `parse_config` before anything is written, so a scanner mistake can only refuse, never
  corrupt. **The dependency is not in this branch**, so there is no dependency request.
- **The question reads stdin even when it is not a terminal.** Git Bash's mintty gives Python a pipe, not a
  console, so a terminal check would lock out a person there. Whether an agent may run the command is its
  own permissions' business (§17.10). The messages and `--help` say that a person must confirm, and that
  `--yes` is only for the operator's own scripts. EOF and a closed or missing stdin count as no answer.
- **Only `yes` counts** (changed after review gate F2): the question says "Type yes", and §17.4 wants an
  explicit confirmation.
- **A relative clip path is made absolute from the operator's working folder.** §17.3 refuses a relative
  path because the daemon's working folder is not the caller's; the CLI's is the operator's own. The
  Windows normalisation this brings is described in Done, step 2.
- **The configuration must load before it is edited.** Otherwise "every other value unchanged" could not be
  checked. So a file with an upper-case hash (which `load_config` refuses) is refused unchanged. The edit
  itself stores lower case and compares without regard to case (tested on the edit function).
- **Over `max_clip_seconds` is a warning, not a refusal**: the limit is configurable. Over 20 MB and a WAV
  of 0 frames are refused: the service can never use them.
- **A read-only configuration is refused, not made writable**: read-only may be the owner's choice.
- **The comment names the clip's resolved path** (the file that was hashed), not the name alone.
- **`list --json`**, as the other commands have.
