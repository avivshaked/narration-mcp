## Done
- **`narration.audition`** (new package), following WP34's pattern (a job kind with a handler in the daemon, and
  results the front-end reads):
  - `variants`: the one reading of a stored request, shared by the handler and `get_results`, so the two cannot
    plan a variant differently. Variant *i* is segment `variant-<i+1>`: the carrier as sent (or the term alone)
    with one hint, `Hint(term, respell, asr_aliases=(respell,))`.
  - `handler`: `AuditionHandler`, the job engine (`JobEngine`) over the daemon's engine core, with its own plan
    (`open`), stages (`AuditionStages`: no measurement key, no scoring facts) and record view (`AuditionView`:
    adds `spk_sim_clip` to the job's result). Rounds, retakes, the cache, leases, failure handling and the
    record are the engine's own code, not copies. One extra piece: the clip's speaker embedding, taken once
    per job in the QA load that scores the takes, with its own retry rules (as `measure_voice`'s clip check).
  - `audition_registry`, and `narration.engine.installed.more_handlers` registers `pronunciation`.
- **Front-end**: `RUNNABLE_KINDS` gains `pronunciation`; `NOT_IN_THIS_BUILD` is now empty (the equality test
  holds). `_step_results`' audition branch now assembles the result from the job's items and the cache
  (`backend.assemble.assemble_audition`, reusing `take_result`), as a generation job's results are: fresh
  `measured_error`, restamped flags, partial results while the job runs. `steps.audition_request` plans each
  variant with the same hint the handler uses.
- **Contracts 1.6.12** (minimal, backward compatible): `AuditionVariantResult.spk_sim_clip: tuple[float | None,
  ...] = ()`, parallel to `takes` and `heard`. Its docstring now also says what `heard` is. Nothing removed or
  renamed; no key, seed, schema id or cached record changes.
- **Texts**: `audition_pronunciation`'s description says what QA it gets and where the similarity is;
  `docs/tools.md` regenerated (`python tools/gen_tool_reference.py`); README no longer lists the tool as not
  runnable (and says it has only been tested on the fake workers).
- **Design revision 5.18** (2026-09-29): header, revision note, and section 7.6's `audition_pronunciation`

## Decisions made (and why)
1. **A variant is a segment with one hint; keys, seeds and the cache are a generation take's.** No new key:
   `keys.seed(voice_hash, engine_text, attempt)` and `keys.render_key`, attempt 0 per variant. So an audition
   sent again renders nothing, and a `submit_job` of the carrier with the chosen respelling as its hint finds
   attempt 0's render already made (Flow D). The segment id (`variant-n`) enters no key (tested).
2. **Cached like takes: yes**, all three layers (render, take, analysis), under the existing keys.
3. **Which checks the verdict has** (section 11.1): signal and token cap, `wer_adj` with the word-count rule,
   terms, head/end insertions and the cue alignment. **No speaker check and no pace check in the verdict**:
   both judge against a measurement, and section 7.6 says the voice need not be measured. The analysis names
   no measurement key, as `AnalysisKeyInputs` already documented for auditions, so a generation request (which
   always names its measurement's key) can never take an audition's analysis for its own. An analysis shared
   with a measurement's calibration take would have the same inputs and the same (speaker-free) rules, so the
   sharing is correct.
4. **WER is against the text as sent, with the term collapsed, and the respelling as the term's one
   `asr_alias`** — not WER against the respelled engine text, as the task suggested. Pushback, with the
   reason: a respelling is an instruction to the engine, not what a recogniser writes. Whisper writes a heard
   name in ordinary spelling ("Torvin", not "Tor-vin" or "TOR-vin"), so scoring the take against the
   respelled text counts a correct rendering as word errors and judges the respelling's orthography, not the
   audio. The alias gives the effect wanted — a take heard saying the respelling counts as saying the term —
   inside the existing rule and key (the alias is in `hints_qa`). Without it, a respelling far from the term's
   spelling is scored as a misheard name, fails `WER_HIGH` and burns retakes (the mutation check above).
5. **Speaker similarity to the clip is reported, not judged**: `spk_sim_clip`, each take's cosine to the
   clip's embedding, in the job's result and in `get_results`, never in a verdict. Putting it in the verdict
   (the clip as the anchor, under measurement key None) would give one analysis key two meanings — speaker
   check on (audition) or off (calibration takes) — so a cached verdict could come back with the wrong rules.
   As a per-job report (like consistency) it has no key. This needed the one contract field.
6. **Retakes, as section 8**, up to `[defaults] max_retakes` per variant: a token-cap or head-insertion take
   says nothing about the respelling. The retake's attempt and seed follow from the request alone.
7. **`heard`** is QA's term window (`TermResult.heard` of the first occurrence), in its normalised form, not the
   raw transcript; the full transcript is in `qa.transcript` with `include_transcripts`.
8. **Results come from records at read time**, not from a result blob the handler writes (the branch used to
   pass `result["audition"]` through). So a running job shows what it has, and the aligner's measured error is
   the current benchmark's, as for generation. The handler writes only `spk_sim_clip` (and the engine's
   suggestions and consistency) to the job's result.
9. **The handler subclasses `JobEngine`** (sharing the daemon engine's core, so no `super().__init__`) rather
   than copying its round and retake logic, as `measure` does. It overrides `open` and `advance`, and swaps in
   its own stages and view.
