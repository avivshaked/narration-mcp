## Decisions made (and why)
1. **The fake lives in `narration_worker`, standard library only.**
   - It then runs from the server venv (CI), from both worker venvs, and through the real entry point
     (`-m narration_worker --role fake`).
   - It writes the float32 WAV header by hand; a server test checks that soundfile reads it identically.
2. **How the fake's "ears" find their text.**
   - **The problem:** QA runs on the *delivery* file (§11.1), which post-processing writes elsewhere. A
     sidecar next to the raw file would never be found there.
   - **The solution:** every 50 ms segment's pitch (120 + 1.5·k Hz) carries one byte of a 32-bit
     utterance id, and a registry under `<store>/scratch/fake/` maps ids to records. Clashing ids step
     on (fix 5).
   - **KNOW** (`workers/common/tests/test_fake.py`, `tests/workers/test_fake_outputs.py`): the id
     survives 48 kHz and 44.1 kHz resampling, gain, trimming, fades and PCM_24/PCM_16. The worst pitch
     error was 0.006 Hz, against a 0.45 Hz tolerance.
   - The audio is integer arithmetic, so it is bit-identical on every platform.
3. **The fault control is the env var `NARRATION_FAKE_SPEC`**, which names a JSON file.
   - The file is re-read when it changes, and strictly validated. An invalid spec crashes the worker at
     start (exit 1, `WorkerCrashed`): it is a test's mistake, not a missing env (follow-up c).
   - No request member, MCP input or store content can set it. A test checks that a request carrying
     `faults` plants nothing.
   - `times` counters are marker files in the store, shared across processes, so a `crash` with
     `times: 1` does not crash the restarted worker too.
4. **stdout guard: KNOW** (the `stdout_noise` fault test).
   - On Windows, `os.dup2(2, 1)` also moves the process's standard output handle, so a child process's
     `print` lands on stderr, not in the protocol pipe.
   - stdin is taken too, so a library that prompts reads EOF instead of a request.
5. **Workers confine paths to `--store`.** Inputs and outputs must be absolute and inside the store, or
   the reply is `INVALID_REQUEST`. This is a second guard behind §17.2's server-side checks.
6. **Role resolution.** `fake` is built in. Real roles register an entry point in the group
   `narration_worker.roles`, named after the role; `--handler module:Class` overrides it.
7. **Client failures.**
   - These all raise `WorkerFailure("BACKEND_NOT_INSTALLED")` (§14: "worker env missing"), with what to
     do next:
     - a spawn failure;
     - a missing venv Python;
     - a worker that exits with `EXIT_START_FAILED` before `hello`, or that has no `narration_worker`;
     - a venv whose base Python is gone (Windows' venv launcher, exit 103, "No Python at");
     - a `hello` that replies `BACKEND_NOT_INSTALLED` (say, torch that cannot load);
     - a role or protocol mismatch in `hello`.
   - Any other exit during start-up is `WorkerCrashed`.
   - A protocol break (non-JSON, no id, an unknown id) is `WorkerCrashed`, and the client kills the
     worker.
   - `request` returns the whole reply, `id` and `ok` included. Its timeout counts from the call.
   - A crash is reported when stdout closes. If a grandchild keeps stdout open, the crash is reported
     within 0.25 s of the process exiting, plus a 5 s grace. It is never waited out to the request's
     timeout.
   - `close()` never blocks on a pipe a grandchild holds.
8. **`worker_env`**:
   - always forces `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1`;
   - sets `CUBLAS_WORKSPACE_CONFIG` from the engine profile, else `[workers] env`, else `:4096:8`, and
     never from the inherited environment;
   - sets the thread-cap variables, and UTF-8 and unbuffered I/O;
   - drops `PYTHONPATH`, `PYTHONHOME`, `VIRTUAL_ENV`, `PYTHONSTARTUP` and `PYTHONSAFEPATH`, so the
     server's Python cannot leak into a worker venv.
9. **The fake's token cap.** Its `load` defaults `max_new_tokens` to 8192 (plan.md §1.3). A lower cap, or
   the `token_cap` fault, cuts the take at a segment boundary and sets `hit_token_cap`.
10. **What the fake answers for.** It transcribes only audio it rendered, or a file listed in the spec's
    `transcripts` (by sha256); anything else gets `UNSUPPORTED_AUDIO`. Its `embed`, `f0`, `align` and
    `profile` answer for any WAV.

## The worker-loop API (for WP20 and WP22; stable from here)
- **Subclass** `narration_worker.handler.WorkerHandler`:
  - set `role` (`"qwen3"`/`"qa"`), `fingerprint_packages` (e.g. `("qwen-tts", "transformers",
    "accelerate", "torchaudio")`), and `controls` (qwen3);
  - implement `op_<name>(self, request) -> dict` for every op of the role except `hello` and
    `shutdown`, returning the reply members without `id`/`ok`.
- **Fail** with `raise OpError(code, message, details)` (`narration_worker.errors`). Validate members
  with `require_str/bool/int/number/str_list/one_of`, and paths with `self.input_file`,
  `self.output_file` and `self.output_dir`.
- **The constructor** must be cheap and must not touch the GPU: no CUDA, no model, no torch import (models
  load in `load`, and `self.torch()` imports torch). An `ImportError` from it, or a handler module that
  cannot be imported (`ImportError` or `OSError`), exits with `EXIT_START_FAILED`, and the daemon reports
  `BACKEND_NOT_INSTALLED`. Any other exception crashes the worker (exit 1, `WorkerCrashed`).
- **Keep the contract** in `handler.py`'s docstring: `NOT_LOADED` before `load`, checked before any file
  is read; `load` checks snapshot dirs first (`BACKEND_NOT_INSTALLED`).
- **Torch.**
  - Get torch with `self.torch()`, which applies the thread cap.
  - In `load`, call `apply_determinism(parse_determinism(request["determinism"]), self.torch())`.
  - Per render, call `seed_everything(seed, torch=self.torch())`.
  - Release models in `shutdown()`.
  - CUDA OOM becomes `GPU_OOM` by itself (`classify`).
- **Register** the handler class:
  `[project.entry-points."narration_worker.roles"] qwen3 = "pkg.mod:Class"`. The lead has decided that
  WP20/WP22 set `package = true` in their worker projects and register the entry point.
- **Start.** To start a worker that will load an engine profile, the daemon passes the profile's
  `determinism.cublas_workspace_config` to `worker_command(…, cublas_workspace_config=…)`.
- **Contract tests:** `class TestQwen3WorkerContract(WorkerContract): role = "qwen3"` in the worker's
  tests, run from its venv. Override the `load_request` fixture to include the load round trip.

## Contract change requests
- none. The earlier request, to drop `from __future__ import annotations` from `protocol.py`, was granted
  in contracts 1.1, and the local adapter is removed.

## Dependency requests

## Follow-ups (re-review)
Branch `wp/16-followups` from `main` 82fe9af; commit 5891e12 (plus this status update). Each fix has a
regression test. Run against `main`'s client, `__main__`, `roles` and `determinism`, 11 of the new tests
fail; the other 3 are guards that already held (listed below).

- **a. A failed worker's writer thread and stdin no longer outlive it.**
  - `_fail` now also queues the writer's stop sentinel. After a crash, a timeout or a protocol break, the
    writer ends and closes our end of the worker's stdin, whether or not `close()` is called.
  - Test: `test_a_failed_worker_leaves_no_pipe_thread_behind_without_close_appA` (crash and hang). No
    thread named `fake-<pid>-*` is left, and `close()` is never called.
- **b. A write error while the worker runs on fails fast.**
  - `_pump_stdin` calls `_write_failed`. It gives the worker `WRITE_FAILURE_GRACE_S` (1 s) to exit, in
    which case the exit is reported as before, with its exit code. Otherwise it calls `_stop("… could not
    be written to … and kept running …")`, and waiting requests get `WorkerCrashed` at once.
  - Test: `test_a_worker_that_stops_reading_is_stopped_at_once_not_at_the_timeout_appA`. A worker closes
    its stdin after `hello` and runs on; the next request fails in under 5 s, against a 10 s timeout.
  - **KNOW (this test), a limit worth knowing:** on Windows a venv's `python.exe` is a launcher. It runs
    the real Python as its child and keeps its own handle to stdin, so the pipe never breaks and this
    fast path cannot fire through a launcher. The test runs the base interpreter directly. A worker
    started through its venv launcher that stops reading is still caught only by the request's
    timeout.
  - For WP30/WP19, the same fact: the pid `on_spawn` gets is the launcher's, not the real Python's. Killing
    the launcher does take its child down; the hang test above shows every pipe closing. BELIEVE that is
    the launcher's own kill-on-close job.
- **c. Start-up failures are classified by cause.**
  - **Too broad, fixed.** `__main__` returns `EXIT_START_FAILED` only for `RoleUnavailable` or an
    `ImportError`, which it logs with its traceback. Any other exception from a handler's constructor
    crashes the worker as usual: exit 1, `WorkerCrashed`, retryable.
    - `handler.py`'s contract now says the constructor is cheap and must not touch the GPU.
    - The fake's invalid fault spec is now a crash too. Its test is renamed
      `test_an_invalid_spec_crashes_the_worker_at_start_wp40`.
    - Tests: `test_a_handler_that_fails_at_start_otherwise_is_a_crash_not_backend_not_installed_appA`
      (a `RuntimeError` in the constructor, and a bad spec); guard:
      `test_a_handler_missing_a_dependency_is_backend_not_installed_with_its_stderr_s14`.
  - **Missed, fixed.** `import_optional` now raises `OpError("BACKEND_NOT_INSTALLED", …, {"module",
    "error"})` for a module that is installed but cannot load:
    - an `OSError` from the import, which is what torch raises on Windows when its DLLs fail;
    - an `ImportError` other than the module itself being absent: a missing dependency, or a failed
      extension. A plain "not installed" was hiding these; for example, a broken numpy would have
      silently gone unseeded.

    A module that is truly absent still returns `None`. `hello` therefore reports a broken torch as
    `BACKEND_NOT_INSTALLED`, not `INTERNAL`.
    - Tests: `test_torch_that_cannot_load_is_backend_not_installed_not_internal_s14` (end to end, a
      stand-in torch whose import raises the WinError 126 `OSError`), and
      `test_a_module_installed_but_unloadable_is_backend_not_installed_s4` (three ways); guard:
      `test_a_module_that_is_not_installed_is_none_s4`.
  - **Same cause, one step earlier.** `resolve_handler` also turns an `OSError` from importing the handler
    module into `RoleUnavailable`, so a handler module that imports torch at the top still gets
    `BACKEND_NOT_INSTALLED` under the narrowed `__main__`.
    - Guard: `test_a_handler_module_that_cannot_load_is_backend_not_installed_s14`.
  - **Optional, done.** **KNOW:** a venv whose base Python is gone exits with 103 and prints `No Python at
    '"<home>\python.exe'`, for a stdlib venv and a uv venv alike. I checked with throwaway venvs under the
    worktree's `.pytest-tmp`, with `home` pointed at a missing folder. The client maps an exit code of
    101–109 with that line to `BACKEND_NOT_INSTALLED`.
    - Test: `test_a_venv_whose_base_python_is_gone_is_backend_not_installed_s14`. It is Windows-only: it
      copies this venv's launcher next to a `pyvenv.cfg` whose `home` is missing. On Linux, a dangling
      venv symlink already fails at spawn (`BACKEND_NOT_INSTALLED`).
