## Decisions made (and why)
- **The lead's decisions on the follow-up report (2026-09-26), recorded here as a handoff.** The branch
  is paused at b98d4a5 plus this status commit; none of them is built yet (see Next).
  1. **Affinity: accepted as built.** Jobs are claimed by priority, then first come. Affinity means the
     resident group is kept across a job boundary; it never reorders the queue. The docstring that
     implements §4 item 3 (`narration.jobs.runner`) must say exactly that.
  2. **One job at a time: the lead's decision, pending the owner.** Cross-job grouping within a round
     is not in this merge; WP31 merges as the one-job-at-a-time engine. The lead puts the grouping to the
     owner as a scope question; if wanted, it becomes a follow-up package on top of this one. Its gain is
     corrected: a Qwen load measured 3.7 s on the H1 run (warm file cache), so a swap pair is likely
     nearer 10 to 15 s than 40 s (BELIEVE; the QA load is not measured yet).
  3. **`embed`'s device: no protocol change.** `"cuda"` means "the GPU the QA group was loaded on" (the
     load's `[gpu] device`). The lead tells WP22 to embed on the loaded group's device. To do: say so in
     the docstring where the engine builds the request (`stages._analyse`).
  4. **The two requests to WP30 are mine, after WP30 merges**, authorised in `narration.daemon` /
     `narration.platform`, each with a test: set `CUDA_DEVICE_ORDER=PCI_BUS_ID` in the workers'
     environment, so `config.gpu.device` is the same GPU for NVML and CUDA; export the daemon log's
     file name from one place, and have `details.log` use it (replacing `runner.DAEMON_LOG`).
  5. **Open items closed:** WP32 assembles `installed_engine`; the lead tells WP22 about `"English"` as
     the ASR language; WP36's result-assembly duties are recorded in HANDOFF.
  6. **Contracts renumber:** WP16's follow-ups, WP30 and WP31 each bumped to 1.6.3 and merge in that
     order, so this branch's `feat(contracts)` commit becomes **1.6.5** after the rebase (a new commit
     or a reword of the unpushed commit).
- **The segment is the unit of the OOM retry** (§4 item 5: "then fail the segment"), for a load and a
  render alike. After the retry, only the take slots waiting for the same stage are failed.
- **A prepare failure is always `UNSUPPORTED_AUDIO`** unless it is OOM, a missing backend or lost
  models. `prepare_voice` only reads the clip and encodes it, and every take needs it. The worker's code
  is kept in `details.worker_code`.
- **Affinity does not reorder the queue.** First come is a strict order (the store's insertion
  sequence), so affinity ranked after it, as the lead ordered, can never decide anything; I added no code
  that cannot run. Ranking it above first come (within a priority) would move jobs away from the queue
  positions DC-2 reports, and could starve an older job. So affinity is what the residency already does:
  the resident group stays loaded across jobs, and a job whose first work needs it starts without a load.
  See Questions, item 1.
- **Lease TTL of 300 s with renewal every 60 s.** Renewal runs on a thread, since a worker request
  blocks the step. A lost lease is not renewed again, and the store publishes the first result.
- **`MAX_CLIP_BYTES` is 20 MiB.** "20 MB" in §17.3; WP36's submit check should use the same constant.
- **The engine refuses to read a caller's path without a check** (`INTERNAL`, not `PATH_NOT_ALLOWED`):
  it is a build fault, not the caller's.
- **A write into the store that fails for another reason than a full disk** is raised as it is, and the
  runner records it as `INTERNAL`.
- **The job record's round never goes back.** A job taken again whose finished rounds are all in the
  cache resumes its round exactly. If a round had an execution error, which is never cached, the error
  is made again, and the record keeps showing the higher round.
- Earlier decisions stand: one piece per step; QA waits for the round's renders; `max_retakes` per slot
  and execution errors not retaken (both confirmed); `analyse` runs the same pipeline;
  `default_runner` fails with `BACKEND_NOT_INSTALLED` until `installed_engine` is assembled (WP32).

## Requests to WP30
- **`CUDA_DEVICE_ORDER=PCI_BUS_ID` in every worker's environment.** NVML numbers devices in PCI order
  and CUDA by default does not, so on a machine with two GPUs the free-VRAM check could read the wrong
  device. The worker environment is built by `worker_command` (WP16) and WP30's supervisor, not by the
  engine. `narration_worker.fingerprint` already records the variable.
- **Export the log file's name** (`LOG_NAME` is in `narration.daemon.__main__`). The engine names the
  log in `INTERNAL` errors (`runner.DAEMON_LOG` = "daemon.log" under `<store_root>/logs/`). An import
  from a `__main__` module is awkward.

## Questions for the lead / owner
1. **Full cross-job grouping within a round (§4 item 3)** is large; the lead decides. It would mean
   holding several queued jobs of one priority and engine profile at once, and running all their renders
   before any of their scoring. It needs:
   - the runner to hold and preempt several jobs, with per-job cancel, progress and drain;
   - a seam change (WP30): `job_started` and `job_finished` per job, and `current_job` becoming a list,
     which changes `get_server_status` (§7.6, a contract change);
   - a design decision on latency. A small job's scores would wait for every other held job's renders.
   - Size: about 300 to 400 lines in `narration.jobs` and 300 of tests, plus WP30's seam and the status
     contract. Roughly two to three days.
   - Gain: one Qwen↔QA swap pair saved per extra job in a round (BELIEVE about 10 to 15 s:
     a Qwen load measured 3.7 s on the H1 run with a warm file cache; the QA load is not measured).
   - Until then, affinity is the residency kept across jobs.
2. **Affinity above first come?** Only if the lead wants it. It changes DC-2's queue positions, and
   needs an aging bound so that an older job is never starved.
3. **The `embed` device** (Contract change requests).
