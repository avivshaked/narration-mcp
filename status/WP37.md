## Done
- **1. The dispatcher** (`src/narration/admin/__main__.py`, `cli.py`):
  - `narration-admin [--config <path>] [-v] <command>`;
  - the configuration comes from `narration.config.find_config`, the rule `narration-mcp` uses:
    `--config`, else `NARRATION_CONFIG`, else `narration.toml` in the service's folder. There is no
    second rule.
  - **The interface for a command group (for WP32's `narration.engine.admin`, and WP38):**
    - a module exposes `register(subparsers) -> None`;
    - `register` adds the group's parser under the group's name in `COMMAND_GROUPS`
      (`subparsers.add_parser("engine", ...)`);
    - on every runnable command it calls `set_defaults(handler=fn)`, where `fn(admin: Admin, args) -> int`
      returns the exit code;
    - `Admin` (`narration.admin.cli`) gives:
      - `config()`, loaded on first use;
      - `config_path()`;
      - `platform()`;
      - `store()` (opened once, closed by `main`) and `store_exists()`;
      - `say()` for stdout and `warn()` for stderr;
    - raise `AdminError(message, exit_code=...)` for a problem the operator can fix; a `NarrationError` is
      printed with its code and hint;
    - exit codes: 0 ok, 1 failed, 2 usage or configuration, 3 not in this build.
  - `COMMAND_GROUPS`, in design §7.1's order:

    | Group | Module |
    |---|---|
    | `install` | `narration.admin.install` |
    | `engine` | `narration.engine.admin` (WP32) |
    | `gc` | `narration.admin.gc` |
    | `verify` | `narration.admin.verify` |
    | `bench` | `narration.bench.admin` (WP38, a name I chose) |
    | `daemon` | `narration.admin.daemon` |
    | `doctor` | `narration.admin.doctor` |
    | `render` | `narration.admin.render` |

    A module that is not in this build gets a stand-in: `--help` shows it as not available, and running it
    says so (exit 3). A module that fails to import, or whose `register` fails or adds no parser, says why
    (exit 1). The other groups keep working either way.
- **2. `daemon start | stop [--now] | status`** (`src/narration/admin/daemon.py`):
  - `start`:
    - calls `ensure_daemon` and waits (`--wait`, 30 s) until the daemon serves;
    - a serving daemon is left alone;
    - when the terminal's job forbids breakaway, it says so and offers `--foreground`, which runs the
      daemon attached until it exits (Ctrl+C: the daemon's own "interrupted; stopping now").
  - `stop`:
    - posts `stop` or `stop_now` **only when `running_daemon` says a daemon runs**, then waits for the
      answer (300 s; 60 s with `--now`);
    - it reports each outcome: stopped (with the re-queued jobs), `stopped: false`, a daemon that exited
      before it read the stop, or a timeout (with what to do next);
    - with no store, it creates none.
  - `status`: prints `run/daemon.json`, whether its daemon still runs and what it holds; `--json` for
    scripts; exit 0 if a daemon runs, else 1.
- **3. `doctor [--quick] [--json]`** (`src/narration/admin/doctor.py`, `models.py`):
  - the checks, each with what to do next for a warning or a failure:
    - platform;
    - config;
    - store root writable, and `min_free_disk_gb`;
    - every pinned model installed, with its files re-hashed against the install record;
    - each worker venv matches its lock (`uv sync --check --locked --offline`);
    - the GPU through NVML (WP44's plain "cannot run jobs" message on a machine with no NVIDIA driver);
    - the engine pin, per kind, from the store (`current_engine_profile`: id, tier, canary).
  - Tried by hand on this machine with a scratch config (gitignored `.dev/try/`), against the dev models
    root and the main checkout's worker venvs. Every check passed except the expected engine warning.
    Hashing every model took 11 s; `--quick` took under 1 s.

## Decisions made (and why)
- **The install record is `<models_root>/manifest.json`**, in the format `tools/dev_models.py` already
  writes: `{"<repo>@<rev>": {repo, revision, snapshot_dir, files_sha256}}`.
  - `install` will write the same file, after checking each file against the Hub's hash at the pinned
    revision.
  - `doctor` and `verify` re-hash against it offline.
  - So a developer's models root is verifiable today.
- **Pins come from WP32's `narration.engine.models.PINNED`**, imported only if it is there.
  - Until WP32 merges, doctor says the pins are unknown and checks what the install record lists.
  - `narration.admin.models.snapshot_dir` repeats WP32's one-line function (`models--<org>--<name>/
    snapshots/<rev>`); switch to WP32's at merge.
- **The engine check reads the store** (`Store.current_engine_profile`, a contract on main), not WP32's API.
  - "Whether the installed stack still matches the pin" is reported as unknown until the engine module is
    in the build.
  - WP32 could expose a doctor hook for that; not needed now.
- **`doctor` changes nothing** except one empty probe file, which it writes and removes in the store root
  (or in its nearest existing parent). It never opens (and so never creates) a store that is not there
  yet.
- `daemon stop` with no store says "nothing to stop" and creates no store.

## Questions for the lead / owner
- **A worker's `BACKEND_NOT_INSTALLED` sticks for the daemon's lifetime** (HANDOFF). The lead's decision
  (plan.md §9) is that `install` stops the daemon after it repairs a worker, and I will build that: it goes
  through `daemon stop`'s rule (it posts only when a daemon runs), and the next job starts a fresh daemon.
  - The alternative, a `reset_workers` daemon command, needs a contract change: `DaemonCommandKind` would
    gain `reset_workers`, and the daemon would drop its workers' sticky errors.
  - I propose it only as a later convenience, and have not built it.
