- **Phase 2, the front-end** in `src/narration/mcp/`, built against `narration.contracts.interfaces.Backend`:
  - `descriptions.py`: every tool's title and description, the server instructions, and the resource and
    prompt texts (sections 7.7 and 7.8). Every description states that no caller state is kept, that length
    is the caller's decision, and that a respelling is a hint. Tools that are not read-only add the DC-2
    backoff rule. Tools that return or take a handle add the retention periods, taken from `RetentionConfig`.
  - `validation.py`: in-handler validation against each tool's published input schema (Draft 2020-12).
    - A failure raises `INVALID_ARGUMENT`, naming the first failing field (shallowest first; an unknown
      field before a missing one), with a hint.
    - Hints: an unknown field such as `instruct`, `style` or `emotion` points to section 3.3;
      `text_mode: "written"` points to section 9.2; a missing field says "Add …"; a size bound says to
      split or shorten.
    - `details.errors` lists up to 20 failures. No message repeats a caller's value.
  - `results.py`: a success result is `structuredContent`, then a JSON text copy, then a `file:///`
    `resource_link` for each absolute path under `path` or `report_md` or inside `pictures`.
    - A Windows path is recognised on any OS. Each link appears once, with a MIME type by suffix.
    - Audio is never inlined.
    - A tool error is `{"error": Error}` built with `serial.to_json`.
    - `INTERNAL` names the exception's type and the log path, never the exception's text.
  - `server.py`: `build_front_end(backend, *, retention, log_path, bus, check_results) -> FrontEnd`
    (`server`, `bus`, `run_stdio()`, `job_updated(job_id)`), on the low-level `Server` (ADR 0001).
    - `tools/list` gives the section 7.1 order, the contract schemas verbatim, and annotations (read-only,
      idempotent, `destructiveHint` only on `cancel_job`, `openWorldHint` false).
    - `tools/call`:
      - an unknown tool is JSON-RPC -32602;
      - a `NarrationError`, including `UnsupportedPlatform`, becomes its tool error;
      - any other `Exception` is logged and becomes `INTERNAL`; cancellation is never caught;
      - every result, success or error, is checked against the tool's `outputSchema`, and a mismatch
        becomes `INTERNAL`.
    - `get_job` gets a progress callback when `wait_s > 0`. The callback drops any report that does not
      advance `progress`. Cancelling the request cancels only the backend's wait.
    - Resources: `narration://status` is in `resources/list`, and the other five are templates. A read is
      matched against the templates, and every variable must be non-empty, before the backend is called.
      The result carries the backend's `ttlMs` and `cacheScope: "private"`.
      - No matching template, or the backend's `NOT_FOUND`, `INVALID_ARGUMENT` or `PATH_NOT_ALLOWED`:
        -32602.
      - Any other failure: -32603, with the Error in `data`.
    - Prompts: the four prompts of section 7.8, with every argument required. An unknown prompt, or an
      unknown, missing or blank argument, is -32602.
    - The list methods and `server/discover` are cacheable for 1 h, private. The default OpenTelemetry
      middleware is removed.
  - `__init__.py` exports `FrontEnd` and `build_front_end`. `__main__.py` is unchanged: it is still a stub,
    until WP36 gives it a real `Backend`.
- **Tests** in `tests/mcp/`:
  - `fake_backend.py`: canned results built from the contract records with `serial.to_json`, with knobs
    for errors, bad results, the job's status (completed, failed or running), progress steps, and a
    blocking wait. It writes nothing to disk.
  - `wire.py`: raw JSON-RPC over memory streams in either era. The legacy era opens with `initialize`;
    the 2026-07-28 era sends its `_meta` envelope on every request.
  - `test_front_end.py` (102 tests) and `test_stdio.py` (2 tests). The stdio tests start the server as
    `sys.executable -m tests.mcp.stdio_server` under a 60 s timeout, and the SDK's stdio client kills the
    process tree on exit.
- `CHANGELOG.md`: one line under Unreleased/Added.

## Decisions made (and why)
- **The backoff rule goes on every tool that is not read-only.** Those are `release_gpu`, `cancel_job`,
  `design_voice`, `profile_voice`, `measure_voice`, `audition_pronunciation` and `submit_job`.
  - Why: the retryable codes (`DAEMON_UNAVAILABLE`, `STORE_FULL`, `QUEUE_FULL`, `RATE_LIMITED`) come
    from writing to the store or commanding the daemon, and the read-only tools only read the store.
  - This is derived from `ToolSchema.read_only`, so it cannot drift from the schemas.
  - The server instructions also state the rule.
- **Every schema failure is `INVALID_ARGUMENT`**, including `maxItems` and `maxLength`. Section 14 defines
  `INVALID_ARGUMENT` as "schema or semantic failure", so `LIMIT_EXCEEDED` is left to the backend's
  configured `[limits]`. There is a question on this below.
- **Results are checked against `outputSchema` at run time** (`check_results=True`). The SDK client rejects
  a success whose `structuredContent` fails the schema, so a backend bug surfaces as `INTERNAL` with the
  failing paths and rules (never values), instead of an exception in the client.
- **`INTERNAL` from the front-end is not retryable**, and it never carries the exception's text, which may
  hold the caller's text or local paths. The text goes to the log (the `narration.mcp` logger, which writes
  to stderr, never to stdout).
- **Progress uses a callback whenever `wait_s > 0`.** It is `ctx.session.report_progress`, which is silent
  without a `progressToken` and also covers the SDK's in-process dispatcher.
- **Resource-read errors**: not-found-like codes are -32602; everything else is -32603 with the
  structured Error in `data`. Section 14 allows no tool error on a read.
- **Resource links** are built by the front-end, because `Backend` returns plain dicts. Only absolute
  paths are linked; the link's name is `<parent>/<file>`.
- **List caching**: 1 h, private. The lists change only with a new server process. The design gives no
  value, so this is my choice.
- **A stdio test with a test-only server module** (`tests.mcp.stdio_server`). The product's
  `python -m narration.mcp` stays a stub until WP36, and no fake ships in the package.

## Questions for the lead / owner
- **Schema size bounds.** When `segments`, `cues` or `hints` exceed their schema `maxItems` (200 / 40 /
  500, the same as `LimitsConfig`'s defaults), should the error be `LIMIT_EXCEEDED` instead of
  `INVALID_ARGUMENT`?
  - For: a consumer would see one code for "too many" whether the schema or a lower configured limit
    refused it.
  - Today: `INVALID_ARGUMENT`, with a hint to split the request.
  - The change would be small, in `validation.py`.
- **What Claude Code sends first** is still unverified, as in phase 1. The server answers both eras, so
  nothing waits on it.
- **Legacy-era clients get no `resources/subscribe`** (as in phase 1). `subscriptions/listen` is 2026-07-28
  only, so they long-poll `get_job`.
