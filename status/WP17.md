## Decisions made (and why)
- The low-level `Server`, not `MCPServer`. `MCPServer` publishes `$ref`, silently drops an unknown field
  (`instruct` succeeded), reports argument errors as text only, and answers an unknown tool with `isError`
  rather than -32602. The low-level `Server` publishes our schemas verbatim and does not validate arguments,
  so section 14 can be done exactly (evidence in the ADR).
- The front-end catches every exception itself. An uncaught one reaches a legacy client as `code: 0` with
  the exception's text, and a modern client as -32603.
- Legacy-era (pre-2026-07-28) clients get no resource subscriptions (`subscriptions/listen` is 2026-07-28
  only). They long-poll `get_job` as the design allows. A `resources/subscribe` handler could be added
  later.

## Contract change requests
- none. Two notes for WP01: (1) `ttlMs`/`cacheScope` belong to each list or read result, not to a
  resource, so section 7.7's table becomes per-read values; (2) the SDK client rejects a success result
  whose `structuredContent` is missing or does not match `outputSchema` (it never checks `isError`
  results). Output schemas should therefore list the success fields plus an optional `error`, with nothing
  required that an error result lacks.

## Dependency requests
- `mcp==2.2.0` (MIT; it requires `mcp-types==2.2.0`, MIT), server project: change `mcp>=2.2,<3` to an
  exact pin. Why: the SDK marks its middleware API provisional ("may change in a 2.x minor release") and
  carries TODOs on exception mapping and the handshake path; the ADR's evidence is for 2.2.0 only. No new
  package; `uv.lock` already holds 2.2.0.
