## Done
- `docs/frontend-plan.md`: the plan.
  - The constraints (read-only, local only, licences, never competing for the GPU) and four rules that follow from
    the code (no write lock and short read transactions; the caller's text never logged; audio by take id, never
    by path; never an MCP tool).
  - A map of every part of the view (jobs and progress, takes with verdicts, flags and a player, failures,
    measured voices, the allowlist, engine pins and the canary, the daemon and the GPU) to the store's tables and
    files, `run/daemon.json`, `failures.collect` / `--json`, and the job, take and analysis records, with the code
    cited. Data not stored today is named (no list of all measurements; the alignment method id; the report files
    exist only after `get_results`; the GPU reading goes stale while the daemon is stopped; which allowlist a
    running daemon read).
  - How to read the store safely while the daemon writes, with a probe (appendix A, KNOW on Linux).
  - Option A (a static report by `narration-admin`) and option B (a dashboard on 127.0.0.1): security (binding,
    DNS rebinding, CSRF, other local users, headers, injection), freshness, dependencies and licences, effort.
  - The recommendation (option A with `--watch`), a phased scope, WP46-A to WP46-E with estimates, nine questions
    for the owner, and what would change the plan.

## Decisions made (and why)
- **The static report is recommended**: no socket (the design's §0 item 11 and §17.1 stand), no new dependency,
  about half the effort; the cost is freshness, which question 1 puts to the owner.
- **A separate read-only reader is required for either option** (KNOW): opening a `NarrationStore` runs a write
  transaction and changed the database file in the probe, it creates a missing store, and its `get_*` reads delete
  rows whose files are gone.
- **The probe lives in the document's appendix, not in `spikes/`**, because step 1 adds documents only; WP46-A turns
  it into a test.
