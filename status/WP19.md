## Decisions made (and why)
- **Mutex namespace `Global\`, not `Local\`.** The store is one folder on the machine. A daemon started
  in another logon session (another user, RDP, SSH) must still be excluded: §4 says two sessions must
  never load two models. Creating a `Global\` mutex needs no privilege (KNOW: tested here). If another
  user's mutex denies access, that counts as "held". The name's prefix and hash scheme must never change,
  or two daemon versions would not exclude each other.
- **The mutex is owned from a dedicated thread.** A Windows mutex is recursive for its owning thread, so
  a second `singleton()` on the same thread would otherwise succeed. The holder thread makes a second
  acquirer in the same process fail like another process, and it lets release run from any thread. A
  holder that dies leaves the mutex abandoned, and the next acquirer gets it (tested).
- **`DAEMON_UNAVAILABLE`** is raised on any `ERROR_ACCESS_DENIED` from `CreateProcess`. Its `details`
  are `{reason: "breakaway_refused", winerror, in_job, job_allows_breakaway}`, and it keeps the code's
  default hint. `retry_after_s` is 10 s, because DC-2 asks every retryable error for one; the value is my
  guess. Any other start failure propagates as `OSError`.
- **Readable paths are checked as text before anything is opened.** The steps are: lexical rules, then
  the drive type (`GetDriveTypeW`, which catches mapped network drives), then a walk through links and
  junctions. The walk checks each link's target as text before following it. This is stricter than §17.3's
  "realpath, then check": `realpath` would already open a share through a local symlink, because Windows
  evaluates local-to-remote symlinks by default. The result has no links left in it.
- **The `PATH_NOT_ALLOWED` `details`** are `{path, rule}`, where `rule` is one of `winpaths.PathRule`:
  `not_absolute`, `network`, `device`, `reserved_name`, `invalid_name`, `no_such_drive`, `not_found`,
  `unreadable`, `not_regular_file`, `link_loop`, `reparse_point`, `outside_root`. Store-path errors carry
  a store-specific hint, because the store's layout is at fault, not the caller.
- **Refused beyond the list in the brief:** alternate data streams (`:` after the drive), wildcard and
  control characters, and a trailing dot or space (Windows drops them, so the name would alias another).
  `COM0`, `LPT0`, `CONIN$` and `CONOUT$` are refused as a precaution, as CPython 3.13's `isreserved` does.
  A known false refusal: a link to a volume that has no drive letter (`\\?\Volume{…}`) counts as a device
  path.
- **Store paths:** any reparse point below the root is refused, cloud-file placeholders included, which
  is what §17.2 says. The root itself may be reached through a link, since the operator chooses it.
  Names that do not exist yet are only checked as text.
- **Kill-on-close:** leaving the block closes the handle and relies on `KILL_ON_JOB_CLOSE`; it does not
  call `TerminateJobObject`. That exercises the same path as a daemon crash. The job handle is not
  inheritable.
- **Venv launchers (KNOW, measured here).** A venv's `Scripts\python.exe` is a launcher, and the
  interpreter runs as its child. So:
  - `set_below_normal_priority` also sets the pid's current descendants, through psutil, which checks
    each process's identity first;
  - `spawn_detached` returns argv[0]'s pid, which is the launcher's;
  - a launcher killed by our job takes its interpreter with it. The kill tests prove this with the
    worker's heartbeat, not by looking at any pid.
- **Tests:** children run `sys.executable` with a tiny script (`tests/platform/_child.py`). Every child
  exits by itself within 15 s. Tests wait only on processes they started, and never enumerate or signal
  other processes.
