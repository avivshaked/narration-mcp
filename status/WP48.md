## Done
- **`narration-admin failures [--since] [--job] [--voice] [--code] [--json] [--export <dir>]`**
  (`src/narration/admin/failures.py`, registered last in `COMMAND_GROUPS`):
  - Lists every take of a `generate` or `analyse` job that **failed QA** (verdict `fail`) or that **a retake
    replaced**, newest job first (the store's queue order, reversed), then in the request's order.
  - For each: job id, kind, status and creation time; the voice clip's sha256; segment id, attempt, seed,
    round and `fresh`; take, render and analysis ids; the delivery WAV's path, sha256 and length; each
    **fail and warn** flag (code, severity, message, cue, details) of its analysis, each once; the analysis's
    QA metrics and thresholds as they are (so WP47's pace fields appear when they land); the take that
    finally filled the slot (attempt, take id, verdict; itself when nothing replaced it); the segment's text
    as the request sent it (cues joined as §7.2 joins them). The text is printed and exported, never logged.
  - Which attempt replaced which is read from the job's `RETAKEN` flags (`details.replaced`), by
    `narration.qa.report.replacements`, which the report uses too: the retake that names the most earlier
    attempts is the slot's last.
  - Filters: `--since` (ISO date or time, UTC unless it names a zone; the job's `created_at`), `--job`
    (checked against the job id grammar), `--voice` (the request's `voice.sha256`, or a prefix, any case),
    `--code` (upper-cased; must be a flag code that can be fail or warn: `RETAKEN` is refused with the list).
    Each bad value is exit 2 with what to give instead. An unknown job is exit 1 and says why it may be gone.
  - Human-readable by default (per job, per segment with its text, each take with its WAV path, metrics
    line and flags); `--json` prints `narration.failures/v1`, described by `FAILURES_JSON_SCHEMA` (JSON
    Schema 2020-12, no `$ref`).
  - A `measure` job's calibration and ladder takes are not listed (the measurement's own probes).
  - A take whose job is still in the store but whose own records left it (collected) is listed with
    `wav: null` and no flags; the export writes only its sidecar and index row.
- **`--export <dir>`**: `<take_id>.wav` (streamed, its sha256 checked against the take's as it is copied),
  `<take_id>.json` (every listing of that take, as `--json` has it), and `index.csv` (one row per listing,
  columns `INDEX_COLUMNS`). A take listed by two jobs is copied once. Each file goes to a `.tmp-` name and
  is renamed with `rename_retrying`, which never replaces a file. Every name is checked first: identical
  bytes are left as they are (so a repeat export is a no-op); **any different file refuses the whole export
  before anything is written** (an auditor's notes in `index.csv` are never lost). A `<dir>` that is the
  store or inside it (textually or after `realpath`) is refused before anything is created (exit 2).
- **The report's "Failures" section** (`src/narration/qa/report.py`): between "Listen first" and "Segments",
  each failed or replaced take with its fail and warn flags and the take that filled its slot. No path.
  `report_json` gains the same list under `failures`.
- **`gc`** (`src/narration/admin/gc.py`): the dry run, the real run and `--json` (key `failures`) show the
  failed or replaced takes apart: how many are in the store, the oldest's age (by the earliest job that
  lists it), and which this run takes out of the audit (the take itself removed, or every job or analysis
  that lists it). The list is read before the collection. **What gc removes is unchanged.** If the list
  cannot be read, gc warns and goes on.
- **`NarrationStore.list_jobs()`** (`src/narration/store/store.py`): every job, newest first; a read that
  records no use. See "Decisions" below.
- CHANGELOG line; README step 5.

## Decisions made (and why)
- **A store method, `list_jobs`** (WP12's file): there was no way to enumerate jobs through the store's API,
  and the lead's brief says to go through that API. The alternatives were a separate read-only SQLite
  connection in `admin` (the store's schema known outside the store) or listing `jobs/<id>/` folders (a
  best-effort copy that can be missing). Easy to move or rename if WP12's owner prefers.
- **"Byte for byte" (KNOW, measured 2026-09-28 with a scratch SQLite script):** opening `NarrationStore`
  runs its idempotent migration in a write transaction (`PRAGMA user_version`), and SQLite then bumps the
  change counter in the database file's header, even with no row changed. Every `narration-admin` command
  that opens the store does this. So the test compares every other file byte for byte (with its mode bits),
  and the database row for row (`iterdump`, which includes every `last_used_at`). A truly byte-identical
  database would need a read-only open mode in the store (and a `mode=ro` connection leaves `-wal`/`-shm`
  files behind when no daemon runs; also measured). Not done; the lead may want it.
- **The store's readers self-heal**: `get_take_by_id` drops an index row whose file was removed by hand. The
  audit reads through that API, so on a store damaged by hand it does what every reader does.
- **Export naming by take id**, not by segment id: segment ids are the caller's (`p01.` or `con` would be a
  bad Windows file name), and a take listed by two jobs is one WAV.
- **`--since` is the job's creation time**: a take has no time of its own in its record.
- **The schema id `narration.failures/v1` lives in `narration.admin.failures`**, not in contracts: it is
  operator output, not a record or a tool. The lead may move it to `contracts.names`.
