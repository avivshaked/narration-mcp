## Done
- **Contracts 1.6.11** (`contracts/names.py`, `contracts/models.py`):
  - `StopReason = Literal["operator", "idle", "interrupted", "error"]`, `STOP_REASONS`, and one constant per
    value (`STOP_OPERATOR`, `STOP_IDLE`, `STOP_INTERRUPTED`, `STOP_ERROR`). No other module spells a value.
  - `DaemonStatus.stop_reason: StopReason | None = None`, the last field, with a default, so it is left out
    of `run/daemon.json` while the daemon runs, and a file with no such key still loads.
  - A `stopped` status now keeps `started_at` (the daemon's own start time).
- **The daemon records why it stopped** (`daemon/status.py`, `daemon/service.py`). `StatusBoard.stopped`
  takes the reason; `Daemon._stop_reason` decides it once, in the `finally` that writes `stopped`:
  - `operator` if the exit answered any stop `stopped: true`, or the daemon read a stop it honours, or it
    honoured a stop the daemon before it had answered (the takeover path);
  - else `interrupted` for a `KeyboardInterrupt` (control loop, supervisor or the way out);
  - else `error` if the control loop raised, the supervisor or the way out raised, or the runner thread
    ended with no stop asked of it (it failed);
  - else `idle` for the idle exit.
- **The runner thread's failure is logged** in the daemon's log (`_runner_main`). Before, it went to
  `threading.excepthook`, that is, to a NUL stderr under a detached daemon.
- **`operator_stop`** (`backend/service.py`): under a status with a `stop_reason`, a queued job waits only
  when the reason is `operator` and a stop answered `stopped: true` was posted after the job was created (no
  timing rule). Under a status with no `stop_reason` (an older daemon's), the 30 s rule is kept unchanged as
  the fallback. `STOP_TO_STOPPED_S`'s docstring says so.
- **`check_launch`** (`daemon/start.py`): its code already compared `started_at >= launched_at` whatever the
  state; only the `stopped` status's null start time made a start-then-stop read as failed. With the start time
  kept, a launch counts as started whenever a daemon recorded a start at or after it, running or stopped, and
  `failed` means no daemon since the launch ever held the singleton. The docstring now says so.
  `_failed_start`'s message ("exited before it served") is therefore true whenever it is given.
- **`narration-admin daemon status`** shows the stop reason of a stopped daemon ("(stop reason: idle)"); its
  `--json` has it in `status`.
- **Design revision 5.17** (2026-09-29): header and revision note; section 4.1 (process identity, the stop
  list with a new "Why it stopped" item, the fallback for an older status, "What remains", the start window,
  "A failed start"); section 15 (`run\daemon.json` line and a bullet). The operator guide's `daemon status`
  line names the reasons. CHANGELOG line under `[Unreleased]` → Fixed.
- `docs/tools.md` needs no change: `DaemonStatus` is not in any published schema (`get_server_status` builds
  its own `daemon` object and does not publish `started_at`). `tools/gen_tool_reference.py --check` passes.

## Decisions made (and why)
- **Keep `started_at`, rather than add a field.** It breaks nothing: every reader that looks at a stopped
  status's `started_at` either checks the state first (`sweep.daemon_alive`, `sweep`) or is `check_launch`,
  whose rule this change is meant to fix. `get_server_status` does not publish it. A new field would also be a
  second key an older reader refuses (below), for no gain.
- **`interrupted` is a reason of its own.** The code can tell a `KeyboardInterrupt` apart, and neither `error`
  (nothing failed) nor `operator` (no stop was posted, so `operator_stop` would find none anyway) is true of
  it. It behaves like `error` for queued jobs: they get a daemon, as they did before.
- **No `superseded`.** No path exists: a daemon that finds another serving exits without writing a status,
  and one that gives up waiting for the singleton writes nothing either. A daemon that takes over and honours
  an answered stop is `operator`.
- **`operator` wins over every other reason** whenever the exit answered a stop `stopped: true`. The answer
  told the operator that the stop held, so the jobs queued before it must wait for the next start, even if
  the daemon also failed on the way out (its log has the failure). Recording `error` there would make
  `get_job` start a daemon the operator had just been told was stopped.
- **Under a `stop_reason`, no timing rule at all.** The status says whether the stop ended its daemon; the
  30 s rule was a stand-in for exactly that. Under `operator`, any stop answered `stopped: true` and posted
  after the job is the one that holds it: a later daemon would have run the job unless it too was stopped by
  a stop posted after the job.
- **`stop_reason` only on a `stopped` status.** While the daemon runs it is left out of the file (the
  serialiser drops a None with a None default), so an older reader still loads a running status.

## Could not settle (for the lead)
- **A daemon that starts and then fails at once is no longer held back by the start window.** This is what the
  approved rule says ("counts a launch as started whenever the start time … is at or after `launched_at`"),
  but it means that a daemon which fails right after it takes the singleton (say, its worker supervisor
  cannot open) is launched again at every `get_job` on a job no daemon serves, one per daemon's short life, at
  the caller's poll rate, instead of once per 90 s. Before, such a daemon read as a failed start and cost one
  launch per window. I built the rule as approved and wrote the case under "What remains" in section 4.1. If
  the lead wants the throttle back for it, one option: when the status says `error` and its `started_at` is
  within the window of the last launch, answer the failed start's `DAEMON_UNAVAILABLE` with a message that
  says it started and then failed (true), rather than launching again.
- **Mixed versions during an upgrade.** `from_json` refuses unknown keys, so a front-end or daemon from before
  1.6.11 that reads a `stopped` status carrying `stop_reason` takes it as unreadable. KNOW (from the code): for
  an older front-end, only `operator_stop` changes: it finds no operator's stop, so it starts a daemon for a job
  a stop left waiting (that daemon runs it). An older daemon taking over treats the previous daemon as died,
  which only makes it sweep (no running job is left under a clean stop). An older `daemon status` says the
  file cannot be read. It ends when the MCP client's server restarts (a reconnect). Written in section 4.1's
  "What remains". Avoiding it would need a field older readers accept, and there is none.
