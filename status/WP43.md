## Decisions made (and why)
- **`docs/tools.md`'s error and flag code tables are shared, not repeated per tool.** The brief says "per
  tool: its description, then its input and output fields as tables … plus the error and flag codes from
  `narration.contracts.codes`." There is no per-tool mapping of which codes a given tool can return in the
  codebase (any tool call can, in principle, hit any error code the front-end's own dispatch or a
  `NarrationError` raises; every result's `flags` can in principle carry any flag code the QA/aligner
  layer defines), so a per-tool subset would either be wrong (a hand-picked guess) or trivially "all of
  them" (no information). I generate one Error codes table and one Flag codes table, once, after the
  per-tool sections, in design section 14's order — the same information, without fabricating a per-tool
  split the source data does not support.
- **Field tables are fully recursive, not top-level only**, using dotted/`[]` paths (e.g.
  `segments[].cues[].exact[].start`). A top-level-only table would hide most of what a caller actually
  needs (e.g. `submit_job`'s `segments[].cues[].exact[]` span rule, or `get_results`' whole `takes[].qa`
  shape). Since every schema is a finite, acyclic tree (no `$ref`, built from nested Python dict literals —
  confirmed by reading `narration/contracts/schemas.py`), recursion terminates on its own; I added a
  40-level sanity guard that raises rather than hangs, purely as a bug trap, since it never fires on the
  current schemas (deepest path is 6 levels).
- **Retention periods in the generated page come from `RetentionConfig()`'s dataclass defaults**, which
  are the same values `narration.example.toml` ships (30 / 365 days) — confirmed by reading both. This
  keeps the generator config-free (it does not need a `narration.toml` to run) while staying accurate for
  the shipped defaults; the page says plainly that an operator's own config may set different ones.
- **README's `uv sync --locked` (not `--frozen`, which the pre-WP43 README used).** `--locked` matches the
  convention already used everywhere else in this codebase for a reproducible install against a committed
  lock file (`narration.admin.install.sync_worker`'s `uv sync --locked`, `doctor`'s `uv sync --check
  --locked --offline`) and fails loudly rather than silently resolving different versions.
- Followed the task's Windows-first path style (backslashes) in commands and config paths, and POSIX
  backslash line-continuation (`\`) in the one multi-line terminal example, since the README already
  targets Git Bash/PowerShell on Windows as the primary shells (AGENTS.md).

## Where the design and the code disagree (as asked in the brief)
- **`CLIP_TOO_LONG`'s retake rule.** `docs/design.md` §14 states it as `never` (a design candidate has no
  take slot for a retake to redo), and the running handler explicitly sets `retake_trigger: false` on it
  in every result (confirmed by reading the design candidate flow and `HANDOFF.md`'s own note on this).
  `narration.contracts.codes.FLAGS[CLIP_TOO_LONG].retake` is still `"always"` in the code, so
  `docs/tools.md`'s generated Flag codes table — which is generated from the code, per the brief's own
  "follow the code" rule — still prints `always`. I did **not** touch `contracts/codes.py` (it is
  lead-owned per AGENTS.md §3, and this exact fix is already a tracked follow-up in `HANDOFF.md`: "a
  contracts fix, the lead's"). `docs/operator-guide.md` has a short section, "Where the design and the
  code disagree", stating this explicitly with a pointer, so a reader of the generated table is not
  misled by it.
