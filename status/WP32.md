## Done
- **1. Engine profiles** (`src/narration/engine/profile.py`, `models.py`):
  - `build_profile(config, kind)` for `qwen3-base-1.7b.pN` and `qwen3-design-1.7b.pN`, from the config,
    the snapshot and the Qwen worker's `uv.lock`:
    - the model pins (`models.PINNED`);
    - every snapshot file's sha256, cached by size and mtime (`FileHashes`);
    - the lock's sha256 and the locked versions of `QWEN_PACKAGES`;
    - the ten sampling values of `generation_config.json`, all required (no library defaults, §10.1);
    - the determinism switches and the DC-4 cap rule.
  - Its hash is `keys.hash_key` over `hashed_object`: every field but `UNHASHED` (`hash`, `snapshot_dir`,
    `observed`, `tier`, `canary`).
  - `current_profile`, `current_ref` and `require_expected` (`ENGINE_CHANGED`, `field` =
    `expect_engine_profile`) are for WP33 and WP36.
  - **A snapshot with an unfinished download** (`*.partial`, hidden or not; WP37's install writes
    `.<name>.partial`) is refused at the pin (`BACKEND_NOT_INSTALLED`, "run narration-admin install
    again"). It is never hashed.
  - `narration.engine`'s package names load `profile` lazily, so `narration.engine.models` imports only the
    contracts (not the store or numpy).
- **2. The fingerprint check** (`drift.py`), which runs after every Qwen load:
  - it compares the hello's package versions and `CUBLAS_WORKSPACE_CONFIG`, the lock's sha256 and every
    snapshot file with the profile;
  - any difference is `ENGINE_DRIFT` (not retryable), with `details.drift` listing each difference (at
    most 20, plus the count);
  - an unfinished download is drift of its own kind, `download`, and its message says to finish the install.
- **3. `installed_engine(host)`** (`narration.jobs.runner` → `engine/installed.py`) returns a `Registry`. It
  holds WP15's `CtcAligner`, the QA pins with their licences, `CanaryGuard` and the NVML probe.
  - A caller's clip is checked by the daemon's platform: `check_path` is unset, which the job engine takes
    to mean `host.platform`.
  - A missing snapshot or an unrunnable `[alignment]` is `BACKEND_NOT_INSTALLED`.
  - `more_handlers(host, engine)` is where WP33 adds `measure`, built on the job engine: see Next.
- **4. The QA group's VRAM need** (`engine/qa.py`), per WP22's spike h (`spikes/h-i-qa-load`):
  - `QA_VRAM_NEED_MB = 11_500`;
  - `QA_MEASURED` writes out the configuration it was measured with;
  - `tests/engine/test_qa_need.py` fails when the pins, the spike's results or the QA worker's load
    settings (revisions, dtype, attention, beams, windows) move away from it. It also fails, rather than
    skips, when one of those files is missing.
- **5. `narration-admin engine pin | repin | bridge | show`** (`engine/pinning.py`, `engine/admin.py`):
  - **What `pin` does:**
    - it designs the canary on this machine (DC-3);
    - it runs the repeat test (two renders in one process, one in a fresh process; all equal is `bit_exact`,
      ADR 0002);
    - it calibrates each threshold with 3 more seeds (the lowest similarity less 0.01);
    - it stores each clip under `engines/<id>/canary.wav`.
  - **Changed installations:** `pin` refuses one and names the fields that differ; `repin` makes a new
    profile the current one.
  - **`bridge`** compares the canary and the calibration paragraphs under two profiles. When the old
    profile cannot render here, it falls back to that profile's pinned embedding.
  - **Workers** are started through WP30's `WorkerSupervisor` (`SupervisedStarter`), exactly as the daemon
    starts them: in the worker project's folder, with `-P`, the offline environment, the thread cap, NVML's
    GPU order, the hardening, the configured priority and a kill-on-close group.
  - **It is registered through WP37's real dispatcher:**
    - it uses `narration.admin.cli`'s `Admin`, `AdminError`, `Handler` and `Subparsers`;
    - a refusal the operator can act on is an `AdminError` that says what to do next;
    - it runs only while no daemon holds the singleton and the GPU has room.
  - `narration.admin.models.snapshot_dir` is now the engine's (the authorised one-line change).
  - `doctor` reads the engine's pins (`pinned_revisions` equals `PINNED`), and reports each pinned profile
    as `ok` with its tier and canary (tested).
- **6. The canary gate** (`engine/canary.py`, `CanaryGuard.after_load`) runs in this order:
  - the fingerprint check, then the canary material's id, then the gate render;
  - an equal hash → `hash_match`, with no QA;
  - a different hash → WavLM-SV alone on the QA worker's CPU (Qwen stays on the GPU), unloaded again
    afterwards: `similarity_pass`, or `ENGINE_DRIFT` below the threshold;
  - a render or embedding the worker fails → `ENGINE_DRIFT`;
  - running out of GPU memory, and a worker that is not installed, are left to the job engine.
- **7. The daemon passes the aligner's method id** to its store (authorised change in WP30's `__main__`),
  so `current_alignment_benchmark` works. An unrunnable `[alignment]` is logged, and the daemon still
  starts.

## Decisions made (and why)
- **The threshold is calibrated, not fixed.** It is the lowest similarity of 3 more seeds, less 0.01. A
  render that diverges like another seed passes; one that differs more fails.
- **The canary's material id** (`canary.v1@sha256:<manifest sha>`) is kept in the `CanaryPin`. Changed
  canary text is drift at the gate, and a pin/repin matter at the pin.
- **The repeat test uses three renders:** two in one process, one in a fresh process (ADR 0002 decision 4).
- **The pin's workers go through the daemon's supervisor**, not `worker_command` alone. The canary must be
  rendered as the daemon will render it, on the same GPU, with section 17's working folder.
- **`engine show` creates no store.** `pin`, `repin` and `bridge` hold the daemon's singleton throughout.

  calibration similarities range from 0.34 to 0.96.
  - KNOW: in the `bit_exact` tier the hash check is exact, so any change of numbers is still seen. The

    two unrelated voices usually are.
  - No job loads the VoiceDesign profile yet; `design_voice` (WP34) will.
  - Base's gate (0.973) is strong, and Base is the path every generate job takes.
  - Options:
    - (a) keep it, as a drift alarm;
    - (b) calibrate VoiceDesign with the same seed and something else varied;
    - (c) give VoiceDesign a fixed floor, e.g. Base's threshold;
