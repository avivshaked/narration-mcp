## Done
- `narration.daemon` (`python -m narration.daemon --store <store_root> --config <path>`):
  - `__main__`: loads the config (a bad one exits 2 before anything is created), checks that `--store`
    is the config's `store_root` (exit 2), and sets the CPU thread cap (WP16's `cap_threads_env`, from
    `[workers] cpu_threads`) before anything imports numpy. The cap is tested with an import hook that
    records the environment at numpy's first import, and the test was mutation-checked. It then sets
    `NoDefaultCurrentDirectoryInExePath=1` on Windows and logs to `<store>/logs/daemon.log` (rotating,
    5 MB × 3). Dev options: `--fake-workers`, `--runner module:Class`, `--idle-unload-s`, `--idle-exit-s`
    and `--poll-s`.
  - `service.Daemon`: creates the store root, then takes `Platform.singleton`. A second daemon exits 0,
    quietly. A daemon that finds the holder `stopping` waits (up to `takeover_wait_s`) and takes over, so
    an idle exit racing a new start does not leave the store without a daemon. It records `os.getpid()`,
    sweeps, serves, and exits on `stop`, `stop_now` or idle. Two threads: the control loop (commands,
    worker deaths, the `stop_now` deadline, status flush) and the runner thread (steps, idle timers).
  - `supervisor.WorkerSupervisor`: one worker per model group (`qwen` → `qwen3`, `qa` → `qa`; both `fake`
    with `--fake-workers`), started through WP16's client with the offline env and the thread caps.
    - Each worker goes into the daemon's kill-on-close group (`add(pid)`) and gets below-normal priority
      in `on_spawn`, before `hello`. Its creation flags are `CREATE_NO_WINDOW` plus
      `BELOW_NORMAL_PRIORITY_CLASS`.
    - The working folder is `[workers.<role>] project`, never the store root. The env has
      `NoDefaultCurrentDirectoryInExePath=1` on Windows, and `PATH` is kept.
    - A worker that crashed is started again on its next use, up to 3 crashes in 300 s.
      `BACKEND_NOT_INSTALLED` is sticky: never retried, and the same error is raised again.
    - `load`, `unload`, `stop`, `release_all` and `kill_all`. At most one GPU group is loaded
      (`one_group_at_a_time`); the policy is WP31's.
  - `status.StatusBoard`: `run/daemon.json`, written through the store on start and on every change. It
    has the state, pid, `started_at`, workers, the current job with its phase, and the GPU facts (holder,
    `in_use`, `unload_in_s` counting down while idle, `need_mb`, `waiting_since`). `est_drain_s` is null
    until WP31 feeds it. A write that fails is written again by the control loop's `flush`.
  - Idle: models are unloaded after `idle_unload_s` (120 s) without a job, and the daemon exits after
    `idle_exit_min` (15 min) without work. Both come from the config, and the tests use values under
    a second.
  - Commands through the store, each completed with a result:
    - `release_gpu` → `{released, holder_before, busy_job}` (`released: false`, naming the job, while
      busy);
    - `stop` → finishes the segment in flight, exits, `{stopped: true, requeued: [...]}`;
    - `stop_now` → kills every worker at once (closes the Job Object), re-queues the job, and exits. The
      runner has `stop_now_grace_s` to give its job back, and the daemon's safety net re-queues it if the
      runner does not.
  - `sweep`: reads the previous `run/daemon.json`. A pid is "ours" only if it exists and was created no
    later than the recorded `started_at` (+2 s); this uses psutil `create_time` only. `running` and
    `cancelling` jobs go back by compare-and-set (to `queued`, and to `cancelled`). A `stop`/`stop_now`
    posted before this daemon started is completed as `{stopped: false, reason}`. Nothing is ever killed
    or inspected beyond that pid's creation time.
  - `start`: `start_detached` (via `Platform.spawn_detached`; `DAEMON_UNAVAILABLE` on refused breakaway,
    no fallback), `running_daemon`, `wait_for_daemon`, `ensure_daemon` for WP36 and WP37. `daemon_python`
    picks `pythonw.exe`.
  - `sweep.read_status`: reads `run/daemon.json` again, briefly, on the two transient Windows errors
    measured in spike (g) part 2 (see Contract change requests).
- **The WP31 seam** (`narration.daemon.seam`, fully documented in its module docstring):
  - `JobRunner` is `step(host) -> bool` (at most one segment; False when idle) and
    `shutdown(host, reason)` (`reason` is `segment`, `now` or `idle`; it runs once, on the runner thread,
    after the last step).
  - `RunnerHost` gives `store`, `config`, `workers` (a `WorkerPool`: `client`, `load`, `unload`, `stop`,
    `loaded`, `gpu_holder`), `holder` (`narrationd`, for claims and leases), `stop_mode`,
    `should_stop()`, `sleep(s) -> bool` (False when a stop is asked), `job_started`, `job_phase`,
    `job_finished`, `set_gpu_facts` and `set_est_drain`.
  - A segment boundary is the return from `step`; the daemon never interrupts a step except by
    `stop_now`, which kills the workers, so the request in flight fails with `WorkerCrashed`.
  - `return_job(store, job_id, reason=)` gives a job back by compare-and-set.
  - Shipped: `NullRunner` (the default until WP31), and `testing.FakeWorkerRunner`. The latter drives the
    fake worker: claim, load, design a clip, prepare the voice, then one `synthesize` per step, with a
    per-call `max_new_tokens` from `names.max_new_tokens_for` and `[engines.qwen3_base]` (DC-4), and a
    `put_render` per segment. It resumes from the render cache.
- Spike (g) in `spikes/g-detached-daemon/`: `spike_g.py` (six scenarios), `status_read_race.py`,
  `results/` and a README with KNOW/BELIEVE/ASSUME. Headlines (KNOW, this machine):
  - a daemon started with `start_detached` outlives its session: plain, via `uv run`, and in a
    kill-on-close job that allows breakaway. After the session is gone it answers `release_gpu`, renders
    a job, and stops on `stop`;
  - without `CREATE_BREAKAWAY_FROM_JOB`, the kill-on-close job kills it when the session exits;
  - a job that forbids breakaway gives `DAEMON_UNAVAILABLE` and no daemon;
  - the `pythonw.exe` daemon has no console. `CREATE_NO_WINDOW` workers have a `conhost.exe` but no
    window.

## Decisions made (and why)
- **The daemon runs as `pythonw.exe`**, which deviates from §4.1's identity table (`python.exe`). A
  detached `python.exe` daemon gets a console of its own (KNOW, spike g). It may show as a window a user
  could close (BELIEVE; not measured). `pythonw.exe` has none (KNOW). The identity marker
  `-m narration.daemon --store <root>` is unchanged. Workers keep `python.exe` (they speak over stdio)
  with `CREATE_NO_WINDOW`.
- **`stop_now` = close the workers' Job Object** (`kill_all`): the request in flight fails at once. The
  runner then has `stop_now_grace_s` (30 s) to give the job back before the daemon exits without it; the
  safety net re-queues it anyway.
- **`BACKEND_NOT_INSTALLED` is sticky** per group for the daemon's lifetime; the job fails with it. The
  daemon must be restarted after `narration-admin install` (see Questions).
- **A crash budget** of 3 crashes in 300 s per group, then `WorkerCrashed` "not started again" until the
  window passes. This stops a restart loop.
- **Idle unload stops the worker processes** (not only `unload`): that frees the VRAM for certain, and
  the next job pays only a process start on top of the model load it needs anyway.
- **The pid check uses psutil `create_time` only**: never the command line (inspection), never a signal.
- **Takeover of a `stopping` daemon**: closes the race between an idle exit and a new start.
- **Stale `stop`/`stop_now`** (posted before this daemon started) are completed without stopping it.
- **`read_status`** works around two store races on Windows (below) on the reading side, inside WP30.
- **Design §17 (for the lead to add, near 17.7)**:
  - workers run with their working folder set to `[workers.<role>] project`, never the store root;
  - on Windows their environment has `NoDefaultCurrentDirectoryInExePath=1`, and so does the daemon's;
  - `PATH` is kept.

  This is because `qwen_tts` imports `sox`, which runs `os.popen("sox -h")` through `cmd.exe`, and
  `cmd.exe` looks in the current folder before `PATH` (KNOW, WP20's review). Tested:
  `test_supervisor.py` reads a started worker's cwd and environment with psutil.

## Contract change requests
- **Store (WP12's code), two Windows races on `run/daemon.json`** (KNOW, `spikes/g-detached-daemon/
  status_read_race.py`):
  1. `get_daemon_status` raises `PermissionError` on about 1 read in 25 while the daemon replaces the
     file. Please retry the read, as `files.publish_temp` retries the rename.
  2. `StoreLayout.confine` compares `os.path.realpath` results. CPython's `ntpath.realpath` returns a
     `\\?\`-prefixed path when the file is replaced between its two looks, and `confine` then raises
     `StorePathError` for a file inside the store. It was seen once in about ten runs of `test_process.py`.
     Please strip the `\\?\` (and `\\?\UNC\`) prefix before comparing, in `confine` and in
     `WindowsPlatform.check_store_path`. `check_readable_path` (§17.3) could likewise refuse, as a device
     path, a caller's file that is being replaced.

  Any reader of a file the daemon rewrites is exposed: the front-end's `get_server_status`, and job
  sidecars. `sweep.read_status` covers the daemon's own reads and `running_daemon`. Once the store is
  fixed, `read_status` can stay as a thin wrapper.
- **Platform (WP19)**: move the daemon's remaining OS-specific choices behind `Platform`. They are small,
  and keyed on `os.name`/`getattr(subprocess, ...)` today, with no banned import:
  - `worker_creationflags` (`CREATE_NO_WINDOW | BELOW_NORMAL_PRIORITY_CLASS`);
  - `harden_env` (`NoDefaultCurrentDirectoryInExePath`);
  - `daemon_python` / `console_python` (`pythonw.exe` / `python.exe`).

  For example, `Platform.worker_process_options(below_normal) -> (creationflags, env_additions)` and
  `Platform.daemon_interpreter(python) -> Path`. Not blocking.
