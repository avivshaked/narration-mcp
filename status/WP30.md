## Second round: the lead's decisions
1. **Which stops a daemon honours** (`620bb6d`). A daemon honours a pending `stop` or `stop_now` only if
   it was posted after that daemon was launched.
   - The handover still works: a daemon launched while the old one was exiting honours a stop posted in
     the gap.
   - A daemon launched later (by `ensure_daemon`, say) completes an older stop with `stopped: false`
     and the reason "it was posted before this daemon was launched, and no daemon running then read
     it". It then keeps serving.
   - If the daemon is already stopping when it reads an older stop, it completes that stop with the
     others as stopped. An older `stop_now` does not hurry it.
   - **Clocks.** Both times come from the wall clock, as `started_at` does.
     - The stop's time is its `requested_at`, which the store cuts to the millisecond. A stop in the
       launch's own millisecond counts as after it (`service.posted_after_launch`), so a stop asked of
       this daemon is never taken for an older one.
     - The daemon's `launched_at` comes from the launcher: `start_detached` passes `--launched-at`, read
       just before the spawn, so a stop posted while the daemon starts up is for it.
     - Without the flag, the launch time is when `__main__` began to run (`BEGAN`). A launch time later
       than that is never believed (`__main__.launch_time`).
     - In-process daemons use their construction time, or a `launched_at` argument.
   - **Docs.** `service.py` ("Which stops a daemon honours"), `start.py` and the package docstring say
     that `narration-admin daemon stop` (WP37) posts only when `running_daemon` says a daemon runs.
   - **Tests: 13.**
     - Both orders, in process: an older stop is answered and not honoured, and the daemon keeps
       serving and runs a job; a stop posted after launch stops it before any work.
     - The boundary, three ways:
       - the predicate on hand-written millisecond stamps (5 cases);
       - a daemon launched 0.5 ms after, 1.5 ms after and 0.5 s before a stop's stamp (3 cases);
       - `launch_time` (3 assertions).
     - `start_detached` passes `--launched-at` from its own clock.
     - A real Windows daemon process honours a stop when `--launched-at` says it was launched before
       the stop, and answers `stopped: false` and keeps serving when it began after the stop.
     - Mutation-checked: with the staleness test disabled, the three tests of the older-stop side fail.
2. **The test platform**, `narration.platform.testing.StandInPlatform` (`cdd52ed`; moved there from
   `tests/daemon/standin.py` in `ed3eb3a`, as you decided).
   - `check_readable_path` applies the real platform's pure text rules first
     (`narration.platform.winpaths.parse_absolute` on Windows). Elsewhere it applies the same rules to a
     POSIX path, so network paths (`\server`, `//server`), device paths (`\?\`, `\.\`) and
     reserved device names are refused on every OS before any file is touched. It then requires the
     path to resolve to an existing regular file.
   - It does not check the drive type, so a mapped network drive is not detected; that is the Windows
     platform's own test's job.
   - `free_disk_bytes` returns `free_bytes`, which a test may set (500 GiB by default). Both methods
     record the paths they are asked about.
   - `check_store_path` refuses with the rule `outside_root`, as the real one does.
   - **The move.** Its behaviour is unchanged. It now has docstrings throughout, and ships as the
     workers' test support does (`narration_worker.testing`).
     - It starts no process. It kills only processes added to its kill-on-close groups, after checking
       their creation time.
     - Its singleton registry is module-level, deliberately: it models the machine-wide mutex namespace,
       so every stand-in in the process shares it.
     - `tests/daemon/standin.py` is gone, and the daemon's tests import the new module.
   - Tests: 22 in `tests/platform/test_testing_platform.py`, moved from `tests/daemon/test_standin.py`
     with two more (a detached spawn starts nothing; the singleton is shared). They include the POSIX
     branch, which Linux CI runs, checked here on every OS.
3. **`read_status` goes through the store's reader** (`f1aa705`, after PR 23).
   - `get_daemon_status` now retries a read that Windows refuses during a rename
     (`files.read_retrying`), and the path check strips the `\\?\` prefix (`platform.real_path`). So
     the daemon's own retry loop, which covered exactly those two cases, is gone.
   - `read_status` now only turns a torn file into `StatusUnreadable`, and raises anything else as the
     store raises it. A test checks that it adds no retries of its own.
   - Spike (g)'s README notes that its part-2 numbers were measured with the old retry.

## Re-review round (merge with follow-ups)
1. **The takeover give-up race** (`c163519`).
   - **The race:** a daemon waiting for the singleton gave up on any holder state but `stopping`. An
     exiting daemon writes `stopped` before it releases the singleton, so a waiter that looked in that
     window exited, and a job queued in the handover was stranded.
   - **The fix:** a waiter now gives up only when the holder says `idle` or `busy`, or at
     `takeover_wait_s`. It treats `stopped`, no status and an unreadable status like `stopping`.
   - Tests:
     - holding the singleton with `stopped`, no status, and a torn status (3 cases), the waiter waits,
       then takes over on release;
     - at `takeover_wait_s` it gives up and writes nothing;
     - a second daemon still exits at once when the holder says `idle`, and writes nothing.

     commit the job first, then read the status. The argument: the daemon writes `stopping`, then asks
     `has_work`, so either its look sees the job, or the front-end's read sees `stopping` and starts a
     daemon.
   - A guard test: after a daemon's last look found nothing, a front-end that commits and then calls
     `ensure_daemon` starts a daemon.

## Decisions made (and why)
- **The daemon runs as `pythonw.exe`**; you accepted this. You update §4.1 at merge. The marker is
  `-m narration.daemon --store <root>`, now preceded by `-P`.
- **`put_daemon_status` stays non-durable**, for the reasons under finding 2.
- **A `has_work` that raises counts as work.** A buggy runner then keeps the daemon up (it still unloads
  its models after `idle_unload_s`) rather than stranding a job. It tries again every `idle_exit_s`.
- **A pending stop is read before the first step and before `idle`**, so a stopped service does no work
  and never looks as if it serves.
- **A daemon's launch time errs early, and a stop's millisecond counts as after the launch.** Both
  choices make a daemon honour a stop that may have been asked of it, rather than ignore one. The
  launcher's `--launched-at` closes the window while the daemon starts up. A stop wrongly honoured costs
  a restart; a stop wrongly ignored leaves the service running against the user's request.
- **The capture rule allows `started_at`'s millisecond, and no more.** `utc_iso` cuts the time to the
  millisecond. A real daemon writes `started_at` hundreds of milliseconds after it starts, so this only
  mattered for the tests' stand-ins. The pid check in `sweep` keeps its 2 s tolerance: it only reads.
- The earlier decisions stand:
  - `stop_now` closes the Job Object;
  - the crash budget;
  - the idle unload stops the worker processes;
  - the pid check uses `create_time` only;
  - the takeover of a daemon that has not said it serves (`stopping`, `stopped`, none or unreadable;
    re-review item 1);
  - `read_status` turns a torn status into `StatusUnreadable` (it is now a thin wrapper over the
    store's reader).

## Proposed wording for design §17 (for the lead; near 17.7, "How the service starts Python")
> The daemon and every worker are started as `<python> -P -m <module> …`. `-P` keeps the working folder
> off `sys.path`, so a module there is never imported in place of the service's own. Their environment
> drops `PYTHONPATH`, `PYTHONHOME` and `PYTHONSTARTUP` (by name, ignoring case), and keeps the rest,
> including `PATH`, the thread caps and the offline flags. A worker's working folder is its project
> folder (`[workers.<role>] project`), never the store root. On Windows, the daemon's and the workers'
> environments set `NoDefaultCurrentDirectoryInExePath=1`. This is because a library the Qwen worker
> imports runs a program through `cmd.exe`, which otherwise looks in the working folder before `PATH`.
> Tests: `tests/daemon/test_supervisor.py`, `test_start.py` and `test_entry.py`.

§4.1's identity table would then read:
- daemon: `pythonw.exe` on Windows (`python` elsewhere), `-P -m narration.daemon --store <store_root>`;
- workers: `python.exe`, `-P -m narration_worker --role <role> --store <store_root>`.

The marker to match is still `-m <module> --store <store_root>`.
