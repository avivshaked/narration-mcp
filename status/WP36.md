# WP36 Front-end to daemon wiring
State: active        Updated: 2026-09-27

Branch `wp/36-backend`, stacked on `wp/31-jobs` at 2cb9905. When WP31 merges, rebase with
`git rebase --onto <new base> 2cb9905` (see **After the rebase**).

## Done
- **M1 ("first narration") works end to end on the fake workers.** Over JSON-RPC in both protocol eras:
  `measure_voice` → `submit_job` (cues, a hint, two takes) → the engine's runner → `get_job` →
  `get_results`. The takes come back with their delivery WAV's path and sha256, placed cue times, QA
  verdicts, and `report.md`. See `tests/backend/test_first_narration.py`.
- **`narration.backend`**, the real `Backend` behind WP17's front-end:
  - `service.NarrationBackend`, with one method per tool. Store calls run in worker threads.
  - `requests`: reads a submission, keeps the request with `[defaults]` filled in (without `dry_run`),
    and gives it an identity (`request_sha256`, which leaves out `label` and `idempotency_key`). It
    refuses `CONTROL_UNSUPPORTED`, and `LIMIT_EXCEEDED` from `[limits]`.
  - `clips`: applies the §17.3 and §17.4 rules. It reads the path only through
    `Platform.check_readable_path`. It refuses a clip over 20 MiB, one whose sha256 differs from the one
    sent, a file that is not a WAV, and one over 30 s. It copies the clip to `scratch/voices/<sha256>.wav`
    before any worker sees it.
  - `planning`: plans the request against the three cache layers with the job engine's own keys. The
    analysis layer is looked up only when `AnalysisPins` are known (WP32).
  - `assemble`: builds `get_results` (§7.5) from the job's items. It restamps cached analyses with this
    request's segment id and exact-span offsets.
  - `views`: `get_job`, `get_server_status` and the queue, with DC-2's numbers from
    `narration.jobs.admission`.
  - `resources`: the `narration://` resources.
  - `launch`: the daemon seam (`DaemonLauncher`, `DetachedLauncher`).
  - `measures`: the WP33 seam (`Measurements`, `StoreMeasurements`).
- **The tools:**
  - `submit_job`: check, plan, then queue; `dry_run` only plans. The same request while its job is
    active is that job (§7.3), and DC-6 refuses a reused key with `field: options.idempotency_key`.
    `RATE_LIMITED`, `QUEUE_FULL` and `STORE_FULL` carry `retry_after_s`. The daemon is ensured only
    after the job is committed. `DAEMON_UNAVAILABLE` leaves the job queued and names it.
  - `get_job`: long-polls until the status changes or `wait_s` ends, with monotonic progress
    notifications. Cancelling the call ends the wait, never the job.
  - `get_results`, including `measure` jobs (`measurement_result`).
  - `cancel_job`, `check_text`, `measure_voice` (at once when current, else a queued `measure` job),
    `get_server_status`, `release_gpu`.
  - `design_voice`, `profile_voice` and `audition_pronunciation` answer `BACKEND_NOT_INSTALLED` until
    WP34 and WP35.
- **`narration-mcp`** serves the real backend on stdio. It finds the config by `find_config`'s rule, and
  a missing or bad config exits 2 with what to do. It logs to `<store_root>/logs/narration-mcp.log`,
  never to stdout. README.md has "Use it from Claude Code".

## Decisions made (and why)
- **No daemon in the tests.** The tests use a `FakeLauncher` plus the engine's runner, stepped as the
  daemon's loop steps it. WP30 is not on this branch. After the rebase, one test will start the real
  daemon with `--fake-workers`.
- **The seams import their module at run time.** `launch` imports `narration.daemon.start` and
  `measures` imports `narration.measure` with `importlib`, so a merge needs no edit. Before those
  modules merge, `measure_voice` counts any stored measurement as current. `narration-mcp` uses
  `narration.config.find_config` when it exists, else its own copy of the rule. The rebase replaces
  all three with direct imports.
- **The stored request has the defaults filled in.** The daemon then runs exactly what the front-end
  planned, and the request's identity does not change when `[defaults]` changes.
- **`AnalysisPins` are optional.** Without them (before WP32), a plan counts every analysis as
  needed, so the estimate is an upper bound.
- **Reports.** `get_results` writes `report.md` and `report.json` for a finished job (temp name, then
  rename), and returns the path of `report.md`.

## Questions for the lead / owner
- `submit_job`'s output `status` enum has no `cancelling`. A submission identical to a job that is being
  cancelled waits up to 10 s, then returns `INTERNAL` (retryable, `retry_after_s` 5). The store's
  `create_job` returns such a job as the active one. Should the store skip `cancelling` jobs when it
  dedupes?
- A request answered entirely from the cache is still queued. The daemon completes it at once, and the
  results are the same. Answering it as a completed job at submit could come later.
