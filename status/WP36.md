# WP36 Front-end to daemon wiring
State: review        Updated: 2026-09-27T14:20Z

Branch `wp/36-backend`, rebased onto `main` at 3cacc47 (WP30 and WP31 merged). WP33 is not merged yet;
see **After WP33 merges**.

## Done
- **M1 ("first narration") works end to end on the fake workers.** Over JSON-RPC in both protocol eras:
  `measure_voice` → `submit_job` (cues, a hint, two takes) → the engine's runner → `get_job` →
  `get_results`. The takes come back with their delivery WAV's path and sha256, placed cue times, QA
  verdicts, and `report.md`. See `tests/backend/test_first_narration.py`.
- **On the real daemon too** (`tests/backend/test_daemon.py`). `submit_job` starts WP30's `Daemon` after
  the commit. The daemon runs on a thread, with fake workers and WP31's `build_runner`. It runs the job,
  and `get_results` returns the takes. A second submission does not start another daemon.
- **`narration.backend`**, the real `Backend` behind WP17's front-end:
  - `service.NarrationBackend`, with one method per tool. Store calls run in worker threads.
  - `requests`: reads a submission, keeps the request with `[defaults]` filled in (without `dry_run`),
    and gives it an identity (`request_sha256`, which leaves out `label` and `idempotency_key`). It
    refuses `CONTROL_UNSUPPORTED`, and `LIMIT_EXCEEDED` from `[limits]`.
  - `clips`: applies the §17.3 and §17.4 rules. It reads the path only through
    `Platform.check_readable_path`. It refuses a clip over 20 MiB, one whose sha256 differs from the one
    sent, a file that is not a WAV, and one over 30 s. It copies the clip to `scratch/voices/<sha256>.wav`
    before any worker sees it.
  - `planning`: plans the request against the three cache layers with the job engine's own keys. The
    analysis layer is looked up only when `AnalysisPins` are known (WP32).
  - `assemble`: builds `get_results` (§7.5) from the job's items. It restamps cached analyses with this
    request's segment id and exact-span offsets.
  - `views`: `get_job`, `get_server_status` and the queue, with DC-2's numbers from
    `narration.jobs.admission`.
  - `resources`: the `narration://` resources.
  - `launch`: starts and reads the daemon through `narration.daemon.start` (`DetachedLauncher`).
  - `measures`: the WP33 seam (`Measurements`, `StoreMeasurements`).
- **The tools:**
  - `submit_job`: check, plan, then queue; `dry_run` only plans. The same request while its job is
    queued or running is that job (§7.3), and DC-6 refuses a reused key with
    `field: options.idempotency_key`.
    `RATE_LIMITED`, `QUEUE_FULL` and `STORE_FULL` carry `retry_after_s`. The daemon is ensured only
    after the job is committed. `DAEMON_UNAVAILABLE` leaves the job queued and names it.
  - `get_job`: long-polls until the status changes or `wait_s` ends, with monotonic progress
    notifications. Cancelling the call ends the wait, never the job.
  - `get_results`, including `measure` jobs (`measurement_result`).
  - `cancel_job`, `check_text`, `measure_voice` (at once when current, else a queued `measure` job),
    `get_server_status`, `release_gpu`.
  - `design_voice`, `profile_voice` and `audition_pronunciation` (in `backend.steps`) check a request
    and queue its job. They do this only when the daemon runs that kind (`RUNNABLE_KINDS`: `generate`,
    `analyse`, `measure`). Until WP34 and WP35 add their handlers, they answer `BACKEND_NOT_INSTALLED`
    at once, so no job is queued that the daemon would fail. When a handler merges, its kind is added
    to `RUNNABLE_KINDS` (one line).
    - `design_voice`:
      - lints the description with WP10's `NegationLinter` (warn, never refuse);
      - holds it to `[limits] max_description_chars` (`LIMIT_EXCEEDED`);
      - runs the design text (the caller's, else `[voice_design] design_text`) through the pipeline's
        refusals;
      - needs a pinned `design` engine;
      - mints the `design_id` at submit.
      The same design while its job is active returns its job and its `design_id`. The identity leaves
      out `name` (the job's label) and `design_id`.
    - `profile_voice`: checks any readable WAV's path, sha256 and format, up to 20 MB (the clip cap).
      It is not held to the synthetic rule or to 30 s (§17.3), and it is not copied.
    - `audition_pronunciation`:
      - needs each variant's label to be unique;
      - needs the carrier to contain the term (the respelling is applied as a hint, so the pipeline's
        own matching decides);
      - applies §17.4 and copies the clip, but does not need a measurement.
    - `get_results` for these kinds returns `design` (the store's candidates under the job's `design_id`),
      `profile` and `audition`. See the proposed result handles below.
- **A job being cancelled** no longer dedupes a new request, and no longer holds its `idempotency_key`.
  This is one `fix(store)` commit, authorised by the lead: `create_job` checks queued and running jobs
  only. It has two store tests and a §7.3 backend test. The design says nothing more about
  `cancelling` for DC-6.
- **DC-2 on every tool.** The backend sets `retry_after_s` on each retryable error it raises. Any
  retryable error from below it (the store, the platform) that has no `retry_after_s` gets its code's
  wait on the way out of every tool (`service.with_retry_after`).
- **`narration-mcp`** serves the real backend on stdio. It finds the config by `find_config`'s rule, and
  a missing or bad config exits 2 with what to do. It logs to `<store_root>/logs/narration-mcp.log`,
  never to stdout. README.md has "Use it from Claude Code", with §16's launch line (`--frozen --offline`),
  using placeholders only.

## Decisions made (and why)
- **Most tests step the engine's runner themselves.** They use a `FakeLauncher` and step the runner as
  the daemon's loop does, which is fast and deterministic. One test runs the real daemon.
- **The real-daemon test runs WP30's `Daemon` on a thread with `fake_workers`,** as WP30's own tests do.
  It does not run a detached `python -m narration.daemon --fake-workers` process. That process would
  run the default runner, and `installed_engine` answers `BACKEND_NOT_INSTALLED` until WP32. A
  `--runner` built from test parts would have to live inside the package: the daemon starts in the
  store's folder with the `PYTHON*` variables scrubbed, so `tests.*` cannot be imported. The detached
  start itself is WP30's, and is tested there.
- **The WP33 seam imports `narration.measure` at run time** (`importlib`), so WP33's merge needs no
  edit. Before it merges, `measure_voice` counts any stored measurement as current. The tests inject
  their own `Measurements`, so they do not depend on the calibration corpus.
- **The stored request has the defaults filled in.** The daemon then runs exactly what the front-end
  planned, and the request's identity does not change when `[defaults]` changes.
- **`AnalysisPins` are optional.** Without them (before WP32), a plan counts every analysis as
  needed, so the estimate is an upper bound.
- **Reports.** `get_results` writes `report.md` and `report.json` for a finished job (temp name, then
  rename), and returns the path of `report.md`.

## Questions for the lead / owner
- **A gap against §7.3:** "When every layer is already in the cache, the job is created already
  `completed`." Today such a request is queued, and the daemon completes it from the cache without
  rendering (tested). The results are the same, but the job is not completed at submit.
  - Doing it at submit means the front-end must fill in the job's items, suggestions, consistency
    report and per-job flags, including cached retakes. That is the engine's completion logic, and
    copying it would be risky.
  - Proposal: a pure function in `narration.jobs`, which WP31 owns, that completes a job from the cache
    or says it cannot. The front-end would call it at submit. Do you want this in WP36, or as a
    follow-up?

## For WP34 and WP35 (proposed; the handlers may change them)
- A `design` job's request: the arguments, with `takes` (default 3), `design_text` (default from the
  config) and the minted `design_id`. Candidates go to the store under that id (`put_candidate`).
- A `profile` job's request is `{audio: {path, sha256}}`. The audio is not copied at submit, so the
  handler stages it, as `stage_clip` does. Its `JobRecord.result` should be
  `{audio_sha256, profile_version}`, from which `get_results` reads the profile.
- A `pronunciation` job's request is the arguments as sent. The clip is already in
  `scratch/voices/<sha256>.wav`. Its `JobRecord.result` should be `{audition: <get_results' audition
  object>}`.
